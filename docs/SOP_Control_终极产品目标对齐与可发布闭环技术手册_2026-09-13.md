# SOP Control 终极产品目标对齐与可发布闭环技术手册

> 日期：2026-09-13  
> 用途：交给第一次接触 SOP Control 的执行模型，独立检查现有实现、识别差距、完成修复并验证到可发布状态。  
> 本手册描述目标产品，不以当前代码结构、已有命名或历史实现为设计上限。现有实现只能作为待检查对象，不能反过来缩减目标。

---

## 0. 执行者必须先理解的结论

SOP Control 是嵌入其他产品的轻量控制平面。它不替代业务产品，不负责生成业务内容，也不自行发明业务语义；它负责让任何执行模型在真实操作产品时，持续遵守该产品已经形成的规则、用户长期保留的细腻要求，以及默认最经济的执行逻辑。

产品由三个永久、平级的规则体系共同构成：

1. **产品本体规则**：随着产品设计、实现和演化形成的事实、约束、入口、状态机和不可违反条件。
2. **动态 SOP**：用户在使用中直接或不经意表达、希望长期保留，但适用情境细、允许一定弹性、触发频率不固定的规则。
3. **自然逻辑**：用户没有逐句说明，但在目标和约束确定后，可以被证明更自然、更省时、更省调用、更少扩大范围的默认执行规则。

这里的“动态”不是“临时”。动态 SOP 与产品本体规则具有同等永久性。它可以在某个上下文中不激活，但绝不能因时间流逝自动消失。只有以下对象允许过期：

- 某次任务编译出的执行计划；
- 能力授权、票据和会话租约；
- 缓存、探针结果和运行证据；
- 用户明确声明为“仅本次”“截至某时”的临时指令。

已经接受的动态 SOP 只能通过明确的修改、暂停、取代或废止动作改变生命周期。不得用 `expires_at`、TTL、长时间未触发、版本升级或模型判断将其自动删除、降级或失活。

最终产品还必须解决第二个母题：**接入与升级**。用户首次接入时不应长期改造产品；以后 SOP Control 升级时，也不应要求每个产品重复手工拉取、修 hook、改 adapter、迁移规则和调试兼容性。

## 1. 产品目标与发布承诺

### 1.1 一句话目标

SOP Control 将产品本体规则、用户不经意形成但需要长期保留的动态 SOP，以及默认最小阻力的自然执行逻辑，共同维护为可生长、可追溯、可执行的永久规则空间；再通过一次接入、完整覆盖、确定性控制和低摩擦升级，把这个规则空间持续作用到产品的每一个真实执行入口。

### 1.2 可发布版本必须兑现的用户结果

安装和接入后，用户应能得到以下结果：

1. 模型换会话、换厂商、换版本后，不会遗忘已经确认的长期规则。
2. 用户日常纠正或表达偏好时，不需要知道应把规则写入哪个文件。
3. 系统能将可能长期有效的表达保存为候选，并用低打扰方式让用户确认。
4. 接受后的动态 SOP 永久存在，在正确情境自动激活，在无关情境保持安静。
5. 模型不能只声称“遵守了规则”；真实产品入口必须经过控制判定或被明确标记为未覆盖。
6. 默认计划应避免先做昂贵全量操作、重复验证、无关扩展和目标满足后的继续工作。
7. 产品业务检查仍由产品执行；SOP Control 负责确保该检查按要求发生并影响后续动作。
8. 初次接入和后续升级都有单一入口、可预览、可验证、失败可回滚。
9. 正常低风险执行不应因为逐动作取票、重复模型审查或冗余账本而显著变慢。

### 1.3 明确的非目标

SOP Control 不是：

- 业务内容生成器、语义 lint 引擎或产品数据库；
- 通用 Agent 可观测平台；
- 操作系统级沙箱或恶意进程隔离器；
- 自动把模型推测升级为产品法律的自治政策作者；
- 产品产物的第二份存储系统；
- 对所有动作都要求人工审批或一次性票据的流程引擎；
- 通过频繁调用另一个大模型监督当前大模型的多代理系统。

发布文档必须诚实说明：SOP Control 控制合作执行者经过受控入口的行为，不宣称能防御拥有同等文件系统权限、主动绕过全部入口的恶意进程。

## 2. 统一概念模型

### 2.1 永久规则与运行实例必须分离

必须存在两个清晰层次：

```text
Permanent Rule Space（永久权威）
  └─ Rule Revision（不可变修订）
      └─ Context Selection（当前情境选择）
          └─ Effective Plan（本次冻结计划，可过期）
              └─ Admission Decision（动作判定）
                  └─ Evidence（最小必要证据）
```

禁止将动态 SOP 只保存在任务 profile、会话记忆、prompt、聊天摘要或可过期 plan 中。运行 profile 是规则的投影，不是规则本体。

### 2.2 统一规则记录

三类规则必须进入同一权威规则空间，使用同一套身份、修订、来源、冲突和生命周期机制。可以保留不同编译器，但不能形成三个互不认识的规则仓库。

建议的最小规则结构如下；现有字段名可以不同，但语义必须等价：

```yaml
rule_id: DR-001
rule_class: dynamic_sop       # constitution | dynamic_sop | natural_logic
revision: 3
statement: "独立审计只检查与 JD 的贴合、事实错误和指定优化，不扩大审计目标"
modality: MUST
status: active               # observed/proposed/active/suspended/superseded/retired
source:
  type: user_utterance
  exact_quote: "..."
  source_ref: "conversation-or-document-reference"
owner: user
scope:
  product: jobsflow
  paths: []
  actions: [materials.audit]
activation:
  all: ["artifact.kind == job_material", "phase == independent_audit"]
flexibility:
  allowed_variance: "仅指定维度内判断，不扩展到无关风格审查"
  lower_bound: "必须核对 JD 贴合与明显事实错误"
  upper_bound: "不得因可解释的小幅夸大触发反复重写"
exceptions:
  policy: explicit_only
conflicts:
  supersedes: []
  superseded_by: null
compiler_targets: [control_profile, required_product_checks]
created_at: "aware UTC"
accepted_at: "aware UTC"
```

### 2.3 生命周期不允许隐式过期

永久规则的允许状态迁移：

```text
observed → proposed → active
active → suspended → active
active → superseded
active → retired
```

约束如下：

- `observed` 和 `proposed` 不是权威规则，不得硬拦截生产动作。
- `active` 必须永久保留，直到显式迁移。
- `suspended` 需要操作者、原因和恢复条件；时间到可以恢复，但不得自动退休。
- `superseded` 必须指向替代规则，并保留完整历史。
- `retired` 必须记录明确理由和操作者。
- 更新软件、迁移 schema、长期未触发都不是合法退休理由。
- 删除永久规则记录属于破坏性动作，正常产品接口不应提供物理删除；只能逻辑退休。

### 2.4 三类规则平级，但适用方式不同

“平级”意味着永久性、可追溯性和进入执行系统的资格相同，不意味着冲突时按类别硬编码优先级。

- 产品本体规则通常作用范围广、表达硬约束。
- 动态 SOP 通常作用范围窄、上下文细、带容忍区间。
- 自然逻辑是默认执行约束；用户或产品明确要求反逻辑行为时，可以通过显式例外覆盖。

不同类别发生冲突时，系统不得静默决定“本体永远高于动态”或反之。只能依据显式 `supersedes`、作用域包含关系、规则修订和例外声明解决。仍无法解决时，应只阻断受冲突影响的动作，并生成一条可理解的冲突说明。

## 3. 支柱一：随产品生长的本体规则空间

### 3.1 应识别的产品事实

系统必须能从产品演化中发现至少以下变化：

- 新增、删除或改名的 CLI、API、hook、插件、脚本和后台任务入口；
- 新状态、状态迁移和并行状态文件；
- 新副作用、写入路径和外部系统调用；
- 新业务检查、完成门和高影响动作；
- 已废弃路径仍然可用、重复入口和绕过路径；
- 文档宣称与真实实现不一致；
- 规则存在但没有生产消费者，或消费者存在但没有对应规则。

### 3.2 生长闭环

必须实现：

```text
Observe → Normalize → Deduplicate → Candidate → Human Enactment
       → Compile → Wire → Probe → Evidence → Observe Again
```

发现应自动、低成本和无感；成为权威规则必须有人确认。不得让模型仅凭猜测自动新增 MUST/MUST_NOT。

每个候选至少包含：来源证据、观察到的事实、建议规则、影响入口、风险、与已有规则的差异、需要人确认的未知项。

### 3.3 真实执行要求

一条本体规则只有同时满足以下条件，才能称为“已执行”：

1. 有权威规则记录；
2. 有明确生产消费者；
3. 消费者位于真实动作路径，而不是只在测试或文档中；
4. 有负向测试证明违反时会阻断或降级；
5. 有实时探针或运行事件证明消费者确实被调用；
6. 删除或断开消费者后，覆盖状态会从 verified 降为 gap；
7. 文档投影不能被当成实际执行证据。

## 4. 支柱二：永久动态 SOP

这是产品的重点能力，优先级不得被自然逻辑或一般规则登记功能稀释。

### 4.1 动态 SOP 的识别对象

不只识别“以后必须”“永久不得”等显式句式，还要识别以下长期信号：

- 用户纠正系统的工作方式，而不是只纠正一次结果；
- 用户说明“我真正想要的是……”；
- 用户反复否定同一类行为；
- 用户解释允许幅度、上限、下限或“不必这么严格”；
- 用户限定某类审查只看哪些方面；
- 用户要求以后减少某类重复验证、扩展思考或 token 浪费；
- 用户给出正例、反例，并说明背后的稳定判断原则；
- 同一偏好跨任务重复出现。

### 4.2 捕获不能打断工作

理想体验不是每句话都弹审批，而是：

1. adapter 将用户原话和最小上下文形成 observation；
2. 确定性规则先识别显式长期或显式临时表达；
3. 对隐含长期表达，可由当前宿主模型提交结构化建议，但模型建议不具有权威；
4. 系统去重、聚合重复纠正并生成候选；
5. 在任务结束、下一次相关任务开始或候选累积到阈值时，用一张简短卡片询问：
   - 记为长期规则；
   - 修改后记为长期规则；
   - 仅本次；
   - 不是规则；
6. 一次确认后永久保存，不再重复询问相同规则。

候选阶段可以等待，已确认规则不能依赖聊天历史才能恢复。

### 4.3 动态规则必须表达“弹性”，而不是只表达开关

至少支持：

- 指定审查目标和禁止扩展目标；
- 事实基线及是否允许质疑基线；
- 容忍区间、上限和下限；
- 首次生成要求与事后修正要求的区别；
- 修正策略：保持、最小修正、重做、升级人工；
- 最大修正轮次和达到条件后的停止；
- 允许模型自由判断的范围；
- 需要调用产品检查的名称和结果要求；
- 上下文选择器：产品、动作、阶段、产物类型、数据集合、操作者；
- 显式例外及其授权方式。

这些字段是通用表达能力，不得写死为 JobsFlow、JD、材料审计或某个单一案例。

### 4.4 规则激活与规则寿命分离

一个动态 SOP 当前未激活，只能意味着选择器不匹配。系统必须能够解释：

```text
规则 DR-001 存在且 active；本次未选择，因为 action=jobs.scan，规则要求 action=materials.audit。
```

禁止输出“规则已过期”，除非它本来就是被明确标记的临时指令。长期动态 SOP 不得有自动 TTL。

### 4.5 执行必须确定性

规则被接受后，选择、合并、冲突判断、预算计数、停止条件和结果判定应尽量由确定性代码完成，不应每次再调用大模型重新解释同一句规则。

允许在候选提取和首次结构化时使用可选 LLM 辅助，但必须满足：

- 保留用户原话；
- 结构化结果必须经过用户确认；
- 运行时不依赖同一个模型继续“理解正确”；
- 没有 LLM 时仍可使用显式规则和已有结构化规则；
- LLM 输出不能直接授予权限或修改权威规则。

## 5. 支柱三：自然逻辑与最小充分执行

### 5.1 定义

自然逻辑不是“模型觉得这样比较好”，而是在给定目标、数据依赖、质量要求和副作用后，可以被证明为更小范围、更低成本且不降低结果质量的默认计划约束。

它至少覆盖：

- 先筛选、排除、去重，再做昂贵处理；
- 只处理目标集合，不扩大到无关集合；
- 有有效缓存时先复用；
- 可批量时不逐项重复调用；
- 已满足目标时停止；
- 用户纠正目标后，旧计划必须失效；
- 同一策略重复失败后停止机械重试；
- 预览与正式执行保持用户要求的同等业务质量，仅改变副作用；
- 完成门作用域与本次目标集合一致，除非全局完成是明确业务不变量。

### 5.2 产品衔接契约

SOP Control 不能凭名称猜测产品操作的语义。每个产品通过 Operator Contract 描述：

- 输入集合和输出集合；
- 前置条件、后置条件和依赖字段；
- 集合基数是缩小、保持、扩大还是未知；
- 成本等级、外部调用数和是否使用大模型；
- 副作用、写入对象和幂等性；
- 是否属于业务规定的 canonical route；
- 产生什么可验证证据。

新入口被发现时可以生成 Operator Contract 候选，但不得自动发明业务依赖。未知依赖必须标记为 `unproven`。

### 5.3 最小充分计划判定

系统不需要搜索全世界所有计划，只需拒绝能够被明确证明为劣势的计划。

计划 A 可以阻断计划 B，仅当能够证明：

1. A 和 B 都满足相同主要目标、质量和必需产物；
2. A 不增加未经授权的副作用；
3. A 在作用范围、昂贵项目数、外部调用、token 或时间上不差于 B；
4. 至少一个成本维度严格优于 B；
5. 依赖关系证明步骤重排不会改变正确结果。

无法证明时不得假装确定。低风险场景可以 warn，高成本或高影响场景可以 `unproven` 并要求补充契约。

### 5.4 标准验收案例

目标：“检索过去一周某职位，把未入表的职位评分并展示。”

正确计划：

```text
时间/职位筛选 → 与台账比对 → 得到未入表集合 → 只对该集合评分 → 展示
```

错误计划：

```text
对全部检索结果评分 → 再与台账比对 → 丢弃已入表评分 → 展示
```

当台账比对不依赖评分结果，评分又属于昂贵操作时，后者必须被判为 `dominated_expensive_step` 或等价结构化原因。若用户明确要求“给全部职位重评分以刷新模型版本”，则这是新目标或显式例外，应允许执行并记录原因。

## 6. 规则编译与运行时控制

### 6.1 有效计划

每次任务开始前，将所有匹配规则编译为 Effective Plan。计划至少冻结：

- 目标和目标集合；
- 适用规则 ID 与 revision；
- 未适用规则及原因；
- 必需产品入口和产品检查；
- 动态 SOP 的容忍区间、修正和停止策略；
- 自然逻辑的计划约束；
- 操作者和能力快照；
- 输入集合或关键产物摘要；
- 预算与副作用上限；
- plan digest。

计划可以因用户纠正、规则修订、输入集合变化或操作者能力变化而失效。失效后必须重新编译，不能沿用旧 digest。

### 6.2 单一准入接口

运行时控制应集中为一个深模块，对调用者暴露尽可能小的接口：

```text
Decision admit(ActionEnvelope envelope)
```

`ActionEnvelope` 至少包含：项目、动作、阶段、目标/任务、输入摘要、副作用、执行者、计划摘要和 adapter 身份。`Decision` 至少包含：pass/warn/block/unproven、reason codes、适用规则、下一步和最小证据要求。

复杂的规则选择、冲突、票据、计划验证、成本控制和证据写入都应隐藏在该模块实现中，不应散落在每个 CLI、hook 和插件里。

### 6.3 产品语义仍由产品负责

若产品规定“render 前必须通过 semantic lint”，SOP Control 应验证：

- 使用了产品声明的 lint 入口；
- lint 检查的是本次受控输入；
- 结果属于当前任务和计划；
- 未通过时 render 被阻断；
- 模型不能用自写理由冒充 lint 通过。

SOP Control 不应自己重新实现该 semantic lint，也不应复制业务产物内容。证据只需保存检查身份、输入摘要、结果、时间、规则和执行入口。

### 6.4 票据和账本的节能原则

票据只用于真正的能力升级、例外、跨权限边界或高影响副作用。禁止所有普通动作机械执行“挑战一次、兑换一次”。

建议分层：

- 只读、低风险、计划内动作：确定性 fast path，无票据；
- 同一任务连续受控写入：使用绑定 task/plan/phase 的短期 phase grant；
- 高影响、越权或例外动作：一次性 capability ticket；
- 人工批准：只在产品规则明确要求时使用。

账本记录最小必要证明，不复制业务内容，不保存 secret，不为每个内部函数调用制造事件。一次逻辑动作最多形成一条 admission 和一条 completion/denial 证据；可以合并时应合并。

### 6.5 判定诚实性

统一结果语义：

- `pass`：已有足够证据证明符合；
- `warn`：允许继续，但存在明确非阻断偏差；
- `block`：已有证据证明违反；
- `unproven`：无法证明符合，也无法证明违反；
- `not_applicable`：规则存在但本次上下文不适用。

不得把缺失证据当作 pass，不得把规则文本存在当作生产执行。

## 7. 一次接入与完整覆盖

### 7.1 外部用户接口应保持小而深

理想的日常接口不应要求用户学习内部模块。建议稳定为：

```bash
sopctl attach <project>      # 首次接入或中途接入
sopctl status <project>      # 查看规则、覆盖、版本和缺口
sopctl rules <subcommand>    # 候选确认、解释和生命周期
sopctl sync <project>        # 检查并完成升级
sopctl rollback <project>    # 回滚运行时/adapter/schema 迁移
sopctl detach <project>      # 安全摘除 SOP Control 自有接线
```

可以保留高级子命令，但普通用户不应为了完成接入而串联十几个命令。

### 7.2 attach 的完整流程

`attach` 内部必须完成：

1. 识别项目语言、包管理器、Git 状态和已有 agent harness；
2. 发现 CLI、API、脚本、hook、插件、后台任务和主要副作用入口；
3. 识别已有规则文档、状态机、测试和业务检查；
4. 生成 Surface Inventory；
5. 为每个 surface 标记 governed、exempt、blocked、gap 或 unknown；
6. 选择已有 adapter 或生成最薄 adapter；
7. 安装稳定 launcher、resolver、hook 和必要投影；
8. 保留外部 hook、插件和配置，所有修改可恢复；
9. 执行真实探针，不接受硬编码 alive；
10. 输出接入报告、覆盖缺口和最小修复建议。

支持两种情境：

- 从产品创建第一天介入；
- 在有大量历史代码、规则和入口的中途介入。

中途介入时不得要求用户先重构整个产品。若产品缺少可接线的 seam，应准确指出最小产品改造，而不是笼统要求“适配 SOP Control”。

### 7.3 “完整覆盖”的定义

完整覆盖不是发现了一部分入口，而是：

- 每个发现的可执行 surface 都有稳定身份；
- 每个 surface 都被分类，最终不存在 unknown；
- 所有高影响 surface 必须是 governed 或明确 blocked；
- exempt 必须有原因、责任人和范围；
- 新增 surface 后能自动回到 candidate/gap；
- adapter 删除、探针失败或入口变化后，verified 必须自动降级；
- 文档、hook 和实际 runtime 的投影一致。

发布前必须在至少两个结构不同的宿主上证明这个 seam 是真实的，例如一个 CLI/hook 密集产品和一个 API/worker 密集产品。只有一个真实 adapter 时，接入抽象仍属于未经充分证明的假设。

## 8. 一体化升级目标

### 8.1 核心原则

产品项目不应复制 SOP Control 的核心实现。应拆分为：

```text
Stable Launcher（一次安装、极少变化）
    ↓
Project Binding（项目绑定和版本锁）
    ↓
Versioned Runtime（核心版本并排安装）
    ↓
Stable Adapter Protocol（产品 adapter）
    ↓
Project Rule Data（项目永久规则，独立于软件包）
```

hook 和 adapter 永远调用稳定 launcher；launcher 根据项目绑定选择运行时。核心升级不需要逐个重写产品入口。

### 8.2 项目绑定清单

每个接入产品必须有由 CLI 管理的绑定记录，至少包含：

- 精确 core version 和更新通道；
- rule schema version；
- adapter protocol version；
- 各 adapter 的版本和内容摘要；
- Surface Inventory 摘要；
- 上一次完整验证结果；
- 当前和上一可回滚运行时；
- 安装方式和 runtime 路径；
- 规则数据迁移版本。

绑定记录不能包含 secret，也不能成为第二份权威规则仓库。

### 8.3 `sopctl sync` 一条命令闭环

理想成功路径：

1. 检查目标版本和签名/摘要；
2. 读取兼容矩阵，生成升级 plan；
3. 在新隔离目录并排安装 runtime；
4. 对规则数据副本执行可逆 schema migration；
5. 重新编译三类规则；
6. 生成语义投影差异：哪些规则选择、强度、消费者或计划结果会变化；
7. 更新或再生成 adapter；
8. 在 shadow 模式运行 attach verify、覆盖探针、负向测试和 gate；
9. 所有门通过后原子切换 launcher 指针；
10. 失败时保持旧 runtime，不影响产品继续运行；
11. 保存回滚点和简短升级报告。

### 8.4 升级硬门

以下任一情况出现，禁止自动切换：

- 任一 active 动态 SOP 丢失、自动过期或无法解析；
- 规则 ID、来源原话或生命周期链损坏；
- 已受控高影响 surface 变成 gap/unknown；
- 规则从 block 静默变为 warn/pass；
- adapter 协议不兼容；
- schema migration 不可逆或回滚测试失败；
- secret 进入命令、日志或 receipt；
- 新版本无法通过真实 probe。

### 8.5 更新策略与用户体感

- patch 版本：可自动下载到 staging；零语义差异且全绿时可以按用户设置自动切换。
- minor 版本：展示一次摘要确认，不要求用户手工执行迁移命令。
- major 或规则语义变化：必须明确确认。
- pinned 项目：只提示，不自动变更。
- 离线环境：支持本地包和摘要验证。
- 正常命令可以低频检查更新，不要求常驻 daemon。

用户看到的理想结果应类似：

```text
SOP Control 0.3.0 → 0.3.1
永久规则 146/146 保留；动态 SOP 23/23 保留
规则语义变化 0；surface 覆盖 18/18
adapter 2 个已验证；回滚点 0.3.0
升级完成
```

## 9. 性能、能耗与 token 预算

### 9.1 设计原则

SOP Control 自身应尽量不调用大模型。运行时控制必须优先使用 schema、摘要、集合关系、状态机、确定性选择器和纯函数判定。

### 9.2 发布预算

执行模型应在项目基准机器上建立 baseline，并满足：

- 稳态低风险 admission 不调用 LLM；
- 内存内纯判定 p95 目标不超过 100 ms；
- 含本地账本/摘要的普通判定 p95 目标不超过 300 ms；
- 对宿主常见工作流增加的中位时延不超过 5%，或有测量证据说明无法达到的原因；
- 只读、低风险动作票据调用数为 0；
- 同一 phase 的连续计划内写入最多获取一次 grant；
- 候选去重和批量确认不得逐条唤醒模型；
- receipt 不复制大型 payload、业务产物或完整命令输出；
- attach/status 使用缓存，代码未变化时不重复全仓昂贵扫描；
- 更新检查不得在每个动作上联网。

如果某项预算因平台差异不能使用绝对数，应给出 baseline 比例、样本数和 p50/p95，而不是删除性能验收。

## 10. 执行模型的工作方法

### 10.1 开始前

执行模型必须：

1. 完整阅读仓库根目录适用说明、README、架构文档和测试入口；
2. 检查 Git 状态，保留用户已有改动；
3. 不直接读写受保护控制目录，所有治理数据变更走产品命令；
4. 记录当前 commit、版本、测试状态和已知失败；
5. 定向搜索实现和调用链，不把大型日志、账本或生成文件整批载入；
6. 不根据本手册假定某功能缺失，也不根据类名存在假定功能完成。

### 10.2 建立目标对齐矩阵

对本手册每项要求标记：

- `PASS`：生产实现、测试和运行证据齐全；
- `PARTIAL`：已有实现，但范围、接线或证据不完整；
- `GAP`：没有实现或不能达到目标；
- `CONFLICT`：现有实现与目标相反；
- `UNPROVEN`：无法获得足够证据。

每一行必须给出代码位置、生产消费者、测试、负向证据和修改建议。不得使用“似乎已经支持”“测试很多”作为通过理由。

### 10.3 修改原则

- 保留已经正确工作的深模块，不进行无目的重写。
- 将复杂性集中到 Rule Space、Compiler、Control Engine、Integration Manager 和 Upgrade Manager 等深模块。
- adapter 只负责翻译宿主产品与稳定接口，不复制规则决策。
- 调用者与测试通过同一 interface；不要只测内部 helper。
- 修改规则 schema 时必须提供迁移和回滚。
- 修复一个入口时同步检查所有同类入口，避免单点补丁。
- 先写关键负向测试，再实现修复；最终删除只验证旧浅模块细节的重复测试。
- 不通过降低门槛、关闭检查、扩大豁免或硬编码探针让测试变绿。

## 11. 实施工作包

执行模型应按依赖顺序推进；已满足的工作包只需补证据，不得重复实现。

### WP-A：目标模型与权威规则空间

交付：

- 三类永久规则的显式分类；
- 统一 Rule schema 和生命周期；
- 动态 SOP 无隐式 TTL；
- 旧规则/profile 迁移；
- 冲突、取代、暂停和退休机制；
- 权威数据与运行计划分离。

验收：动态 SOP 经进程重启、换模型、换会话和软件升级后仍存在；长期未触发不会消失；临时指令不会被错误永久化。

### WP-B：动态 SOP 捕获与确认

交付：

- 用户原话 observation 接口；
- 显式、隐式和重复纠正信号；
- 候选去重、聚合和来源保存；
- 低打扰确认流程；
- 通用弹性、范围、修正和停止表达；
- 无 LLM 的降级路径。

验收：没有“永久”关键词的稳定纠正也能成为候选；模型建议不能直接生效；同一候选不反复询问；用户选择“仅本次”后不会进入永久规则。

### WP-C：统一编译器与确定性判定

交付：

- 上下文选择；
- 规则合并与冲突检测；
- Effective Plan 和稳定 digest；
- 规则、输入、操作者、任务和产品检查绑定；
- 失效与重编译；
- pass/warn/block/unproven/not_applicable。

验收：规则未激活时可解释原因；旧 plan 在用户纠正后被拒；缺证据不能 pass；类别本身不作为冲突优先级。

### WP-D：自然逻辑 MSE

交付：

- Goal Contract；
- Operator Contract；
- Set Lineage；
- 计划成本向量；
- 可证明安全的局部重排与支配规则；
- 显式反逻辑目标/例外。

验收：通过本手册 5.4 案例；未知产品依赖产生 unproven 而不是猜测；计划优化不降低质量或删除必需步骤。

### WP-E：产品 adapter 与 Surface Inventory

交付：

- 稳定 adapter protocol；
- 自动 surface 发现；
- Operator Contract 候选；
- governed/exempt/blocked/gap/unknown 分类；
- 新增、删除、改名后的漂移检测；
- 至少两个结构不同的真实 adapter 或等价生产级参考集成。

验收：所有高影响入口有确定分类；删除 adapter 或让 probe 失败时覆盖降级；外部 hook 和插件不被破坏。

### WP-F：单一运行时准入与节能

交付：

- `admit(ActionEnvelope)` 深模块；
- fast path、phase grant 和高影响 ticket 分层；
- 产品检查结果绑定；
- 最小 receipt 与 secret 脱敏；
- 性能和调用数测量。

验收：普通读操作零票据；多步骤计划不逐动作挑战；产品 semantic check 未通过时规定动作受阻；SOP Control 不复制业务产物。

### WP-G：一条命令 attach

交付：

- 绿地和棕地发现；
- plan/apply/verify/status/detach；
- 稳定 launcher；
- adapter 自动选择和最小 gap 指南；
- 备份、权限保留和失败回滚；
- 完整覆盖报告。

验收：在干净样例和历史项目各运行一次；无 harness 时不乱建目录；有外部 hook 时正确链式接入；detach 只移除自身资产。

### WP-H：一条命令 sync 与回滚

交付：

- 项目绑定清单；
- side-by-side runtime；
- 兼容矩阵；
- 可逆 schema migration；
- adapter 再生成；
- semantic projection diff；
- shadow verify、原子切换和 rollback。

验收：成功升级只需一个用户动作；升级失败不影响现有产品；所有永久动态 SOP 保留；模拟断电或中途失败后能恢复到一致状态。

### WP-I：文档、安装与发布包装

交付：

- 中文和英文 README 语义一致；
- 五分钟接入示例；
- 动态 SOP 从日常表达到永久规则的完整示例；
- 自然逻辑示例；
- 升级和回滚示例；
- 支持矩阵、威胁模型和非目标；
- 版本、changelog、安装包和 release notes。

验收：新用户不阅读源码即可完成安装、attach、确认一条动态 SOP、查看 status、执行 sync 和 rollback。

## 12. 必须具备的测试矩阵

### 12.1 永久规则

- 三类规则都能创建、修订、暂停、取代和退休；
- 动态 SOP 不因时间、重启或升级过期；
- 临时指令不会进入永久空间；
- 来源原话和历史完整；
- 非法生命周期链 fail-closed；
- 规则冲突可解释且不静默放宽。

### 12.2 动态 SOP

- 显式长期表述；
- 无“永久”关键词的行为纠正；
- 同义重复纠正去重；
- 允许区间和上下限；
- 限定审查目标；
- 最大修正轮次和达到条件即停；
- 仅本次规则；
- 上下文不匹配时 not_applicable；
- 模型伪造“用户已确认”被拒。

### 12.3 自然逻辑

- 筛选、去重先于昂贵操作；
- 缓存优先；
- 不扩大目标集合；
- 目标满足即停；
- 用户纠正使旧计划失效；
- 重复失败策略停止；
- preview 保持质量；
- run 级 gate 不得错误阻塞 set 级目标；
- 显式反逻辑目标可以执行；
- 未知依赖不被推断为安全。

### 12.4 接入覆盖

- CLI、API、hook、插件、脚本、worker；
- 绿地和棕地项目；
- 外部 hook 共存；
- adapter 删除和探针失败自动降级；
- 中途 attach 失败完整回滚；
- detach 保留外部资产；
- Windows、macOS、Linux 的真实或明确支持矩阵。

### 12.5 升级

- patch、minor、major；
- core、schema、protocol、adapter 分别变化；
- 规则语义零变化升级；
- 有语义差异时阻断自动切换；
- migration 中断；
- adapter 不兼容；
- probe 失败；
- rollback；
- 动态 SOP 和历史记录 100% 保留。

### 12.6 安全与诚实性

- ticket 重放、错 task、错 action、错 plan；
- secret 在 argv、环境、日志、异常和 receipt 中脱敏；
- 伪造 alive/verified 被拒；
- 直接跳过产品检查不能获得 pass；
- 未覆盖入口明确为 gap；
- 不宣称沙箱级不可绕过。

## 13. 发布门

只有同时满足以下条件，才可以判定“可发布”；否则必须明确标为 beta、preview 或未完成：

### 13.1 功能门

- 三类永久规则都有端到端生产路径；
- 动态 SOP 的隐含捕获、确认、永久保存和运行时执行闭环；
- 自然逻辑通过标准案例和至少三个跨领域案例；
- 产品业务检查可以被声明、调用、绑定和强制；
- 一次 attach 和一次 sync 成功路径完整；
- 失败可回滚；
- 所有高影响 surface 无 unknown。

### 13.2 工程门

- 全量测试、lint、类型/静态检查、包安装 smoke、Git diff check 全绿；
- 总 branch coverage 不低于 85%，规则编译、生命周期、升级事务和准入关键模块不低于 95%；
- 关键负向测试齐全；
- clean environment 可安装；
- 支持平台矩阵有真实证据；
- P0/P1 缺陷为 0，P2 缺陷有明确延期理由且不破坏产品承诺。

### 13.3 产品门

- 至少两个结构不同的真实宿主完成接入和升级演练；
- 用户无需改业务核心即可完成基础接入；
- 存在产品缺口时，报告能准确指出最小改造位置；
- 低风险正常路径无显著票据摩擦；
- 中文和英文产品承诺一致；
- README 不夸大语义质量、恶意绕过防护或“零改造全覆盖”。

### 13.4 性能门

- 满足第 9 节预算，或存在经过批准的、有数据的例外；
- 无稳定态 LLM 依赖；
- 无逐动作双调用票据循环；
- 大仓库扫描有增量缓存、上限和可解释降级；
- 日志、receipt 和上下文流量有明确上限。

执行模型完成后必须严格按以下结构报告，不能只给测试数量或主观评分。

### A. 最终结论

- 当前版本/commit：
- 发布判定：GA / Beta / Preview / Not Ready

## 15. 最终完成定义

本手册的完成，不是“增加了三个模块”“测试达到某个数量”或“README 写了目标”。完成必须同时证明：

1. 三类规则都进入同一永久规则空间；
2. 动态 SOP 不依赖显式关键词才能被候选化，并且接受后永不隐式过期；
3. 规则能被编译到真实产品动作，而不只存在于文件中；
4. 自然逻辑能阻止可证明的浪费，同时允许用户明确要求的反逻辑行为；
5. 产品语义由产品执行，SOP Control 能证明规定检查确实发生；
6. 所有真实 surface 被发现、分类和验证；
7. 普通路径的控制收益高于时间、token 和票据成本；
8. 初次接入只需一个主要命令；
9. 后续升级只需一个主要命令，并且失败不伤害现有产品；
10. 永久动态 SOP 在任何升级、重启、换模型和换会话后完整保留；
11. 发布门全部有可复现证据；
12. 对尚未证明的能力诚实标注，而不是通过文档或模拟结果宣称完成。

达到这十二项，SOP Control 才成为一个真正“小而精”的产品：规则空间足够完整，运行接口足够少，控制逻辑足够确定，接入和升级足够轻，且不会为了证明控制而制造比模型漂移本身更大的成本。
