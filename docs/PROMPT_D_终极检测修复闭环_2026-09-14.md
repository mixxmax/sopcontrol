# SOP Control × JobsFlow 终极检测与一次性修复闭环手册

## ——交给未接触过本项目的外部模型执行

> 这是一个“先独立复现，再直接修复，最后重新验收”的执行手册，不是只写报告的审计手册。
>
> 目标是一次性处理两份独立验收报告中已经发现的问题，继续查找同类问题，分别修复 SOP Control 和 JobsFlow 应负责的部分，完成回归测试，并给出可以发布的最终结论。
>
> 外部模型必须把本手册当成完整工作包执行，不要只修复第一个报错，不要发现一个问题就停下来等待用户，不要把未验证写成通过，也不要用修改后的测试结果掩盖修改前的失败。

## 1. 给执行模型的最高优先级指令

你现在接手两个相互连接的代码库：

- SOP Control：控制规则、动态 SOP、自然逻辑约束、admission、ticket、证据、桥接、升级和 CLI；
- JobsFlow：实际业务产品，负责检索、筛选、评分、材料、入表、导出以及与 SOP Control 的 adapter 接入。

本次工作必须同时完成四件事：

1. 在干净副本中复现两份验收报告的 FAIL；
2. 继续执行针对性测试，找出报告没有覆盖的同类问题；
3. 直接修改对应代码、测试、文档和 vendor pin，直到所有可修复问题闭环；
4. 在修复后的同一版本上重新执行 JobsFlow 实效测试和 SOP Control 内部测试，并提交最终证据。

### 1.1 不允许的行为

你不得：

- 直接修改或删除正式工作区中的用户未提交改动；
- 使用 git reset --hard、git checkout --、git clean -fd 或等价破坏性命令；
- 直接编辑或删除任一项目 .sopcontrol/ 内的控制器文件；
- 关闭 enforce、hook、adapter、ticket 或正式 gate 来制造通过；
- 使用 --no-verify、跳过测试、跳过用户确认或直接调用内部私有函数代替正式产品入口；
- 把测试 fixture 伪装成真实宿主或真实外部平台；
- 把 FakeDistiller、静态源码或旧报告当成真实 LLM 或真实 JobsFlow 效果；
- 为了让结果变绿而放宽验收标准、降低 coverage 门槛或删除失败用例；
- 用模型自报“已审计”“已确认”“已遵守”替代独立来源的证据；
- 把一次性规则写进永久规则空间；
- 让用户为了普通安装、更新或正常工作手工编辑多个内部文件。

### 1.2 可以做的事情

你可以：

- 创建干净的临时 worktree、临时测试项目和隔离 fixture；
- 修改 SOP Control 和 JobsFlow 正式代码；
- 增加或修正测试、CLI、adapter、文档和版本 pin；
- 使用正常 CLI 运行测试并让测试副本产生 receipt、ledger、候选和规则状态；
- 在修复代码后提交 commit；
- 运行完整回归、静态检查、gate、coverage 和产品入口 smoke test。

除非用户另行明确要求，不要 push 到远端。最终报告中给出 commit、工作树状态和需要 push 的分支信息。

## 2. 本次修复必须遵守的产品目标

不要根据自己的偏好重新定义产品。下面的目标是验收基准。

### 2.1 三类平级、永久的规则

#### 产品本体规则

随着产品构建形成的长期产品法律、流程、状态和必经入口。它通常较强硬，例如正式写入口、状态转移、不可越过的前置检查。

#### 动态 SOP

用户在自然对话或工作过程中不经意表达、但希望长期保留的细节规则，包括：

- 用户真正希望审查的目标；
- 不希望模型扩张的审查范围；
- 已确认事实基线的处理方式；
- 允许合理灵活处理的上限和下限；
- 何时修正、何时不修正；
- 最大修正轮数和停止条件；
- 某条规则适用的 action、phase、task 或 scope。

动态 SOP 中的“动态”表示来源和内容可以随产品运行逐步形成，不表示有时间 TTL。只要用户没有明确废止、替换或声明一次性，它就是永久规则，与产品本体规则平级。

#### 默认自然逻辑

用户没有逐字说出、但在当前目标下最自然、最少阻力、最少重复工作、最节能且最符合目标的默认执行顺序。

标准例子：

~~~text
检索过去一周标题符合 paralegal 的职位，找出还没有入表的岗位，给这些未入表岗位评分并展示。
~~~

默认应当是：先按时间和标题筛选，再排除已入表，再只对未入表子集评分，最后展示或推进下一步。

自然逻辑是默认约束，不是绝对禁令。用户明确说“这次故意先全量评分做实验”时，系统应允许该例外，并且不能把一次性例外沉淀为永久默认规则。

### 2.2 SOP Control 的职责边界

SOP Control 不负责替 JobsFlow 发明业务语义，也不负责决定 JD 是否真的匹配。JobsFlow 负责业务语义和产物质量。

SOP Control 必须确保 JobsFlow 按其已定义的系统设计运行：

- 必须经过的业务检查不能被跳过；
- 用户设定的动态审查目标、容忍度、修正策略和结束条件不能被模型自行扩张；
- 用户确认的规则可以长期保存、被正确选择和实际生效；
- 未确认建议不能取得权威；
- 默认自然逻辑可以减少无必要工作；
- 明确例外可以被允许；
- 控制结果必须真实影响 JobsFlow 正式入口，而不只是写 receipt。

### 2.3 效率目标

不要把“更安全”简单实现成更多 ticket、更多人工确认、更多重复审计或更多 LLM 调用。

必须尽量满足：

- 只读动作低成本，能零 ticket 则零 ticket；
- 同一 phase 或 operation 内合理复用一次授权；
- 自动学习只在有足够信号时提案；
- 普通闲聊、系统报错、一次性指令不会制造规则噪声；
- 失败后可恢复且不会重复外部副作用；
- 用户安装和升级不需要手工改造 JobsFlow 多处代码。

## 4. 工作目录和版本处理

### 4.1 识别两个仓库

先执行只读检查：

~~~text
pwd
git status --short --branch
git rev-parse HEAD
~~~

分别在 SOP Control 和 JobsFlow 目录执行。若实际路径不是历史记录中的路径，以当前文件系统为准。

### 4.2 建立隔离副本

不要在脏工作区直接实验。为本轮工作建立：

1. JobsFlow 基线副本：从 4f3a08b 或当前明确的 JobsFlow 验收基线创建；
2. SOP Control pin 副本：从 JobsFlow 实际 pin 指向的 SOP Control commit 创建；
3. SOP Control 最新开发副本：从当前待修复 HEAD 创建，用于将修复合并到最新代码；
4. JobsFlow 修复副本：从 JobsFlow 基线创建，用于更新 vendor 和 adapter。

如果某个 commit 不存在，先记录缺失，不要猜测或自动改用 main。可以使用临时 detached worktree；不得用 reset 破坏正式目录。

### 4.3 记录实际导入版本

在 JobsFlow 修复副本中，以正式入口检查实际导入：

~~~text
python3 -m tools.workflow --help
python3 -m tools.workflow learn --help
~~~

再使用当前项目已有的诊断或 Python 入口打印：

- sopcontrol.__version__；
- sopcontrol.__file__；
- vendor pin；
- JobsFlow commit；
- 实际 adapter 使用的模块路径。

不要仅执行 JobsFlow 根目录的裸 import 就下结论。真正要证明的是正式 tools.workflow 入口导入了正确的 vendor。

### 4.4 版本策略

修复 SOP Control 后，不能只改 source 而让 JobsFlow 继续使用旧 vendor。必须：

1. 生成明确的 SOP Control 修复 commit 或 release commit；
2. 更新 JobsFlow 的固定 pin 和 vendor snapshot；
3. 确认两个 pin 文件一致；
4. 运行 JobsFlow 的正式入口；
5. 再运行 JobsFlow 侧测试；
6. 报告实际导入版本和源码摘要。

禁止把 pin 改成 main、master、latest 或浮动分支。

## 5. 第一轮：先复现再归因

修复前先建立一份 baseline 报告。每个问题至少保存：

- case ID；
- 基线 commit 和 vendor pin；
- 正式命令或用户输入；
- 预期行为；
- 实际行为；
- traceback 或关键输出；
- 是否产生了外部副作用；
- SOP Control decision、rule ID、task/run/operation 摘要；
- 是否属于 SOP Control、JobsFlow 或双方边界。

### 5.1 归因方法

对每个 FAIL，做两个最小复现：

#### Core-only 复现

在 SOP Control pin 副本中，通过公开 CLI 或公开 API 复现，不经过 JobsFlow。

#### Product-entry 复现

在 JobsFlow 修复副本中，通过 python3 -m tools.workflow 或实际产品入口复现。

归因规则：

- Core-only 已失败：优先修 SOP Control；
- Core-only 通过、Product-entry 失败：优先修 JobsFlow adapter/CLI/接线；
- 两者都通过但真实行为仍失败：修 JobsFlow 业务计划或正式入口接线；
- 两者输出矛盾：先修版本、导入路径或测试环境，再判定功能；
- 只有真实外部平台无法运行：代码问题不自动判 FAIL，但必须标 UNPROVEN，并尽量用 L1/L2 fixture 补齐。

### 5.2 不得用“模型发挥”结案

如果用户给出了明确目标，而 JobsFlow 走了另一条流程，必须判断是：

- 目标没有被解析；
- 计划没有生成；
- 自然逻辑没有接入；
- 动态 SOP 没有被选择；
- 业务入口绕过了控制；
- run 级门禁把实现方便错误地变成了业务目标。

不能只写“模型理解有偏差”就结束。

## 6. P1 修复包一：动态 SOP 确认后必须长期生效

### 6.1 要修复的问题

当前报告指出：

~~~text
learn decide --route control 只落到 candidate，进不了 effective_rules。
~~~

这意味着用户明确确认的动态 SOP 没有取得长期控制权，动态规则的核心闭环断裂。

### 6.2 目标状态

一条动态 SOP 必须经历清晰状态：

~~~text
observed -> candidate/proposal -> user_confirmed -> compiled/effective -> selected -> enforced
~~~

具体要求：

- 自动观察和模型建议只能进入 observed/candidate；
- 用户明确选择 keep/confirm 或等价 control 路由后，才可以进入权威规则空间；
- control 路由必须真实写入规则权威、编译有效 profile，并能被选择器选中；
- 新会话、新进程、重新加载后仍然存在；
- 规则只在匹配的 action/phase/task/scope 中激活；
- 不匹配范围不能激活；
- 重复确认幂等，不产生重复规则；
- 用户编辑后的版本必须是最终权威正文；
- once_only、reject、not_a_rule、defer 都不能进入永久 effective rules；
- 用户撤销或替换后，未来任务不能继续使用旧规则；
- 历史证据可以保留，但历史存在不等于当前激活。

### 6.3 实施步骤

1. 阅读 SOP Control 的 LearningProposal、动态规则、registry、compile、selection、CLI decide 实现和现有测试；
2. 阅读 JobsFlow learning_adapter 的 decide_learning_proposal 实现；
3. 对比 control、document、both、once_only 等 route 的状态转移；
4. 找出 candidate 写入点和 effective_rules 加载点之间的断点；
5. 修复最小的正式状态转移，不要新增第二套平行规则存储；
6. 让 JobsFlow adapter 调用公开能力完成确认，不要直接写 SOP Control 私有文件；
7. 确认所有写入都通过 sopctl 公共命令或公开 service；
8. 增加 core-only 和 JobsFlow-entry 两层测试；
9. 做新进程/新会话重载测试；
10. 检查无效 route、重复 route、旧 proposal 和 scope mismatch。

### 6.4 必须通过的用例

~~~text
DS-01：观察事件 -> review，只生成 candidate，Registry 不增长。
DS-02：candidate -> defer，仍为 candidate，不激活。
DS-03：candidate -> reject/not_a_rule，永久 Registry 不增长。
DS-04：candidate -> once_only，只在当前会话/任务可见，重启后不成为永久规则。
DS-05：candidate -> control，进入 effective rules，产生明确规则 ID 和编译摘要。
DS-06：新进程加载 DS-05 规则，并在匹配 action 上实际改变 JobsFlow 行为。
DS-07：不匹配 action 不选择 DS-05。
DS-08：对 DS-05 重复确认，不创建第二条等价规则。
DS-09：edit 后，旧正文不再作为当前有效正文。
DS-10：撤销/替换后，未来任务不再激活旧规则。
~~~

### 6.5 严格失败条件

出现以下任一项，继续修复，不得报告完成：

- CLI 显示 control 成功但 Registry/effective rules 没有变化；
- Registry 有规则但新进程加载不到；
- 新进程能加载但选择器不激活；
- JobsFlow adapter 自己写候选文件冒充 SOP Control 规则；
- 任何未确认模型建议直接进入 effective rules；
- once_only 进入永久 Registry；
- control 结果没有用户可追踪的 proposal/source/digest。

## 7. P1 修复包二：intake --dry-run 不得 traceback

### 7.1 要修复的问题

报告指出，JobsFlow 的正式 intake --dry-run 入口会直接抛出：

~~~text
UserPromptError: confirm_manual_intake
~~~

并且带不带 URL 结果相同。这不是可接受的用户交互，也不能算作安全阻断。

### 7.2 目标状态

dry-run 必须是无副作用的计划/验证动作：

- 不写入真实业务产物；
- 不创建不必要的 ticket；
- 不直接抛出未处理 traceback；
- 如果需要用户确认，应返回结构化状态，例如 needs_user/confirmation_required；
- 输出明确说明缺少什么、确认什么、下一步是什么；
- 不应要求用户猜测内部异常名；
- `--dry-run` 的结果应和正常 intake 的计划阶段一致，但不能执行实际写入；
- 如果参数组合不合法，应返回清晰的 usage 或 validation error；
- 真正执行 intake 时仍然必须经过正式控制入口。

### 7.3 实施步骤

1. 查看 intake 的 CLI parser、dispatcher、UserPromptError 定义和 JobsFlow user_prompt 处理；
2. 复现以下组合：

~~~text
intake --dry-run
intake --dry-run <合法 fixture>
intake <合法 fixture>
intake --help
~~~

3. 判断 confirm_manual_intake 是缺参数、状态机错误、dry-run 误走写路径还是异常没有被转换；
4. 将“需要确认”与“程序错误”分开；
5. 让 CLI 输出结构化 JSON 和人类可读文本两种形式；
6. 为 dry-run、确认、拒绝、真正执行各加测试；
7. 通过正式 tools.workflow 入口重跑，不得只测内部函数。

### 7.4 必须通过的用例

~~~text
INT-01：合法 fixture + dry-run，退出码符合当前契约，无 traceback，无副作用。
INT-02：缺少用户确认，返回结构化 needs_user，不是 Python traceback。
INT-03：用户确认后，正常 intake 可以继续。
INT-04：用户拒绝后，不产生写入，不进入半完成状态。
INT-05：非法参数返回清晰错误，不签发空 ticket。
INT-06：重复 dry-run 幂等，不重复写产物或重复弹窗。
~~~

如果产品设计明确要求 intake 必须人工确认，也必须把它表达成产品状态，而不是未捕获异常。

## 8. P1/P2 修复包三：学习噪声、一次性规则和提案边界

### 8.1 必须区分四种输入

自动学习管线收到的内容至少分成：

1. 用户长期规则信号：用户纠正、反复强调、明确要求以后保持；
2. 用户一次性要求：只针对本次任务或实验；
3. 普通闲聊或低价值上下文：没有可复用行为规则；
4. 系统/工具错误与运行状态：不是用户规则，不能被提炼成行为规则。

### 8.2 闲聊和系统错误不能自动制造提案

当前报告发现 FakeDistiller 可能把闲聊或系统错误提炼成 proposal。修复目标：

- 普通闲聊只保留为必要的上下文，不进入规则候选；
- 系统 traceback、工具失败、网络波动、临时重试不进入规则候选；
- 没有用户意图主体的事件不能自动生成动态 SOP；
- 单个低置信度事件不应立即弹窗；
- 同一指纹、同一错误、同一操作不重复提案；
- 观察事件和提案生成必须有明确触发阈值；
- 用户明确使用 learn 时可以提高提取优先级，但仍不能越过确认；
- 如果仍使用 FakeDistiller，必须诚实命名为确定性测试/规则提取器，不得声称具备真实 LLM 泛化能力。

### 8.3 建议的最低触发规则

实现时至少要求满足以下条件中的一项：

- 用户明确使用 learn 或等价显式入口；
- 用户明确纠正模型并包含未来行为、以后、下次、默认、不要再、始终等长期意图；
- 同一工作目标中出现两次以上相互一致的纠正；
- 用户明确给出可复用的边界、例外或容忍度。

以下内容默认不得触发永久动态 SOP：

- 普通问候、闲聊、感谢；
- 单次工具失败或系统错误；
- 单次网络超时、重试、凭据缺失；
- 没有用户主体的业务数据内容；
- 仅仅是模型自我总结；
- 用户明确说“这次”“仅本次”“实验一下”的要求。

不要把关键词匹配写成唯一权威。关键词只能作为低成本信号，最终仍要有来源、scope、候选状态和用户确认。

### 8.4 一次性实验不得污染永久规则

对“这一次故意先全量评分”的实验，必须同时保存：

- 一次性范围；
- session/task ID；
- 用户明确的一次性原话摘要；
- 不进入永久 Registry 的原因；
- 当前任务结束后不可作为默认自然逻辑的证明。

不能把一次性文本直接拼接进永久 candidate 正文，然后靠用户“照单确认”让它变成永久规则。提案正文必须把长期规则候选与一次性背景分开。

### 8.5 必须通过的用例

~~~text
LR-01：普通闲聊 10 条，不产生 proposal、不弹窗、不注册规则。
LR-02：系统报错 5 条，不产生 proposal、不注册规则。
LR-03：同一用户纠正重复两次，合并为一个候选，不重复弹窗。
LR-04：用户明确“以后都这样”，产生候选但不直接生效。
LR-05：用户明确“这次这样”，只产生 once_only/session 记录。
LR-06：候选正文不把一次性实验条件伪装成永久要求。
LR-07：模型自发建议但用户没说过，只保留 suggestion/candidate。
LR-08：prompt injection 只作为业务文本，不取得学习和控制权。
LR-09：相同事件重放，提案和规则均幂等。
LR-10：用户 reject/not_a_rule 后，未来相同文本不会自动恢复成有效规则。
~~~

### 8.6 噪声严重度判定

- 仅内部 candidate、无用户提示、无永久写入：P2；
- 会对用户频繁弹窗或干扰正常工作：P1；
- 未确认就进入 effective rules：P0/P1；
- 系统错误可改变未来 JobsFlow 行为：P1；
- once_only 可污染永久规则：P1。

## 9. P1 修复包四：package apply 不得先发空 ticket

### 9.1 要修复的问题

报告指出 package apply 可能在确认实际 package 存在、内容合法、目标路径可写之前就签发 ticket。这样会造成：

- 无效动作消耗授权；
- 票据账本出现无法对应真实 operation 的记录；
- 用户重试时产生更多无效票据；
- 控制面看似严密，实际顺序错误。

### 9.2 正确顺序

必须遵守：

~~~text
参数校验
  -> package/manifest/目标存在性检查
  -> 计算 canonical payload 和 operation_id
  -> 预检查不会产生副作用
  -> 仅在确认将执行真实高影响动作时 challenge ticket
  -> admit/redeem
  -> 执行一次 apply
  -> 写 receipt
~~~

若没有 package、package 为空、manifest 无效、目标 scope 不匹配或命令只是在做 dry-run，不得先发 ticket。

### 9.3 必须通过的用例

~~~text
PK-01：package 缺失，返回结构化错误，零 ticket，零副作用。
PK-02：package 为空，零 ticket，零 receipt 或明确 validation receipt。
PK-03：manifest 非法，零 ticket。
PK-04：dry-run，零写入，零高影响 ticket。
PK-05：真实 apply，先完成 preflight，再发一次正确绑定的 ticket。
PK-06：ticket challenge 后执行前 package 被改变，admit 拒绝，不能应用旧票据。
PK-07：apply 重试不重复外部副作用。
~~~

如果当前产品约定所有动作都需要 ticket，也必须区分“预检查失败”与“真正准备执行的动作”；不能为了形式上的 ticket 让无效输入也消耗授权。

## 10. P1 修复包五：ticket secret 必须安全处理

### 10.1 先区分必要传递和泄露

票据 secret 可能需要从签发方传递给下一次正式 admit 请求，但不能出现在：

- 普通 CLI 人类可读输出；
- receipt、ledger、chronicle；
- exception traceback；
- shell 命令回显或日志；
- 测试报告；
- JobsFlow 用户提示；
- debug summary；
- telemetry 或临时文件明文。

如果必须在机器间传递，应使用当前设计的受保护 handoff、父进程内存传递或明确脱敏的结构化通道。不要简单删除 secret 导致正式兑换再次失效。

### 10.2 实施步骤

1. 搜索所有 ticket secret 的生成、返回、打印、序列化、异常和 receipt 路径；
2. 对 CLI、bridge、adapter、subprocess、shell wrapper 分别检查；
3. 保留正式调用需要的内部值，但所有人类输出和持久化记录统一 redact；
4. 检查短 secret、长 secret、嵌套 JSON、argv、env、shell -c、异常字符串等形式；
5. 增加负向测试，扫描输出中不得出现原 secret；
6. 增加正向测试，脱敏后正式 operation 仍能完成一次兑换；
7. 检查 ticket 过期、消费和清扫，不留下可重放明文。

### 10.3 必须通过的用例

~~~text
SEC-01：正常 challenge 输出不包含原 secret。
SEC-02：admit/redeem 失败输出不包含原 secret。
SEC-03：receipt、ledger、chronicle 不包含原 secret。
SEC-04：argv、env、shell wrapper 日志不包含原 secret。
SEC-05：嵌套 payload、JSON、异常和 debug summary 均脱敏。
SEC-06：脱敏不影响正式 admit/redeem。
SEC-07：错误 secret、旧 secret、重放 ticket 仍然拒绝。
~~~

## 11. 第三类问题：自然逻辑必须从“存在能力”变成“实际生效”

两份报告都没有完成自然逻辑的真实 JobsFlow 运行证据。这不能继续只写 UNPROVEN 后结束；要先补 fixture 和正式入口测试，能修的直接修。

### 11.1 标准场景

创建隔离数据：

- 过去一周符合关键词的岗位：至少 10 条；
- 其中已经入表：至少 6 条；
- 未入表：至少 4 条；
- 评分、语义检查和入表动作都可观察；
- 不需要访问真实外部网站。

执行用户目标：

~~~text
过去一周标题含 paralegal 的岗位，找出未入表的，给未入表的评分并展示。
~~~

### 11.2 通过条件

- 计划先完成过滤和入表状态判断；
- 只对 4 条未入表对象进行评分；
- 已入表的 6 条不会被重复评分；
- 与当前目标无关的 pending 不会被强迫清零；
- 只读预览输出的是管线质量预览，不是绕过管线的原始清单；
- JobsFlow 用户可见结果和控制证据保持一致；
- 记录实际评分对象数、调用数、耗时和重复工作量。

### 11.3 显式反逻辑实验

重新执行：

~~~text
这一次故意先给全部候选评分，用来比较顺序；这是一次实验，不要改变以后默认规则。
~~~

通过条件：

- 允许这次反向顺序；
- 说明这是显式例外；
- 不污染永久自然逻辑；
- 下一次普通请求仍恢复默认经济顺序。

### 11.4 修复归属

- 如果自然逻辑 selector/plan 在 SOP Control 单独测试中就不工作，修 SOP Control；
- 如果 SOP Control 能生成正确计划但 JobsFlow 不执行，修 JobsFlow adapter/engine；
- 如果计划正确但业务执行仍评分全量，修 JobsFlow 业务执行器；
- 如果 run 级 gate 把无关 pending 设为当前任务必需条件，修控制范围绑定，不要让模型清理无关对象来适应错误门禁。

## 12. 第四类问题：完整写管线与真实接入

### 12.1 L1 先闭环

在没有真实外部数据凭据时，使用隔离 fixture 先完成：

~~~text
scan/preview
  -> 初评分
  -> 语义检查状态
  -> audit gate
  -> proposal/confirmation
  -> ticket/admit
  -> controlled write/intake
  -> receipt/result
~~~

每一步必须通过 JobsFlow 正式入口执行。不能只调用生成材料的内部函数。

### 12.2 外部真实场景

真实网络、真实 portal、真实宿主、跨平台和真实 LLM 如果当前环境没有条件，不要为了“全部修复”伪造结果。你要：

- 用 L1/L2 fixture 补足可以由代码验证的部分；
- 把真正依赖外部环境的项目单列为 UNPROVEN；
- 检查代码是否已经提供可执行的接入、诊断和失败提示；
- 说明补做 L3 所需的最小条件。

“无法在当前机器访问真实网站”是环境证据缺失，不等于代码可以不测试。

### 12.3 真实审计边界

JobsFlow 如果要求材料审计，测试审计目标必须固定为用户设定的范围：

- 是否贴合 JD；
- 是否有明显事实错误；
- 是否有不合理夸大；
- 是否接受已确认事实基线；
- 是否不把合理工作过程夸大强行改回；
- 是否不扩张到用户未要求的全方位审计。

SOP Control 的验收重点是：JobsFlow 规定的审计步骤是否真的经过、审计结果是否进入正确门禁、审计范围是否被动态 SOP 锁定。SOP Control 不应自行发明语义判断。

## 13. 第五类问题：升级、vendor 和一体化接入

### 13.1 修复后必须更新 JobsFlow

修改 SOP Control 后，JobsFlow 不会自动变化。必须执行明确的 vendor 更新流程：

1. 在 SOP Control 修复副本提交修复；
2. 生成可识别的 release commit/version；
3. 更新 JobsFlow tools/sopcontrol_pin.txt；
4. 更新 vendor/sopcontrol/PIN.txt；
5. 更新 vendor/sopcontrol 代码快照或安装来源；
6. 确认两个 pin 文件完全一致；
7. 执行 JobsFlow 的 import-path 诊断；
8. 运行 JobsFlow 正式入口；
9. 再执行 JobsFlow 侧回归。

不要假设 `pip install -U sopcontrol` 会自动改变 vendored JobsFlow。必须证明正式入口实际使用了新版本。

### 13.2 一次接入检查

对 JobsFlow 执行当前支持的诊断命令，通常包括：

~~~text
python3 -m tools.workflow doctor
python3 -m tools.workflow attach-status
python3 -m tools.workflow --help
~~~

对 SOP Control 执行当前支持的诊断命令，通常包括：

~~~text
sopctl doctor
sopctl compat
sopctl gate
~~~

命令名称必须以实际 help 为准。

检查：

- 安装一次后是否能发现正式入口；
- 绿地项目和棕地项目是否都能接入；
- CLI、API、worker 或 agent 入口是否有明确覆盖状态；
- third-party hook 是否被保留；
- detach 是否能移除自己的接线而不破坏他人 hook；
- 缺少宿主时是否明确报 gap，而不是伪造 adapter_alive；
- 更新 vendor 后是否不需要手工改 JobsFlow 多处业务代码；
- 更新失败或版本不匹配时是否保持旧版本可用。

### 13.3 升级必须通过的用例

~~~text
UP-01：无规则语义变化的修复版本升级，JobsFlow 正常运行。
UP-02：动态 SOP 100% 保留，且新进程可加载和选择。
UP-03：目标版本丢失动态 SOP，升级阻断或要求明确确认。
UP-04：目标版本放宽已有控制规则，升级阻断或要求明确确认。
UP-05：迁移中断后重试，不产生半迁移状态。
UP-06：回滚后旧版本可用，动态 SOP 不丢失。
UP-07：vendor pin、实际 import path、版本号和源码摘要一致。
UP-08：JobsFlow 无需重新手工改造多处业务入口。
~~~

## 15. 测试成本与能耗

修复过程中必须测量，不要凭感觉宣布“低成本”。至少执行 5 次并记录中位数和 P95：

- 普通只读任务耗时；
- 受控写入任务耗时；
- 实际外部 LLM 调用数；
- 本地 selector/gate/distiller 调用数；
- token 或近似 token；
- ticket challenge/redeem 数；
- 用户提示数；
- 重复评分/重复审计对象数；
- 失败重试数。

特别区分：

- “没有外部 LLM 调用”；
- “调用了本地确定性 FakeDistiller”；
- “调用了真正的 LLM”；
- “虽然 token 为零，但存在 CPU/I/O/进程调用成本”。

验收目标：

- 只读路径不因控制面增加高额摩擦；
- 一次 phase 内合理复用授权；
- 学习提案不是每条消息一次；
- 默认自然逻辑比反向全量处理明显更节省；
- 用户不需要理解内部 ticket、digest 和 ledger 才能工作。

python3 -m pytest -q

## 17. 修复完成条件

只有同时满足以下条件，才可以写“本次修复完成”：

### 17.1 已知问题

- dynamic control confirm 已从 candidate 进入 effective rules，并在新 JobsFlow 会话实际生效；
- intake --dry-run 不再 traceback，状态和副作用符合契约；
- 闲聊、系统错误和普通失败不会制造用户噪声提案；
- 一次性实验不会污染永久规则正文或 Registry；
- package apply 不会在无 package/无效输入时先发空 ticket；
- capability ticket secret 不出现在 CLI、receipt、ledger、traceback、日志和报告；
- 每个已知问题都有回归测试和最小复现记录。

### 17.2 核心产品目标

- 三类规则平级、永久、可解释；
- 未确认候选无权威；
- once_only 不入永久空间；
- 默认自然逻辑真实影响 JobsFlow 执行顺序；
- 明确反逻辑要求可以作为一次性例外；
- 动态审查目标、基线、容忍度、修正策略和停止条件不会被模型擅自扩张；
- 正式业务入口的控制结果真实改变行为；
- 接入和更新不要求用户手工改造多处业务代码。

### 17.3 质量和版本

- JobsFlow vendor pin 与实际导入版本一致；
- SOP Control core-only 测试通过；
- JobsFlow-entry 测试通过；
- 完整测试、静态检查、gate、project check 和 chronicle check 通过；
- 无新增 secret 泄露；
- 无 P0/P1 未关闭；
- P2 有明确修复或可接受的发布后计划；
- 真实 L3、跨平台或真实 LLM 如果无法运行，必须明确列为 UNPROVEN，不得冒充 PASS。

## 19. 不要来回询问的执行决策表

遇到普通实现选择时，直接按下表处理：

| 情况 | 直接决策 |
|---|---|
| 两份报告分数不同 | 不取平均；按同一矩阵重测，已知 FAIL 优先处理 |
| core 通过、JobsFlow 失败 | 修 JobsFlow adapter/正式入口 |
| core 失败 | 修 SOP Control |
| 不知道是否应永久保存 | 默认候选，不写 effective；需要用户确认 |
| 明确“这次/实验” | once_only，不进入永久 Registry |
| 普通闲聊/系统错误 | 不生成规则提案 |
| 用户明确长期规则 | 生成候选，确认后进入 effective |
| 用户明确反逻辑 | 允许本次例外，不改变默认逻辑 |
| dry-run 需要确认 | 返回结构化 needs_user，不抛 traceback |
| 输入无 package | 先返回 validation error，零 ticket |
| 输出中可能有 secret | 保留内部兑换能力，所有外部展示统一 redact |
| 缺真实外部网站 | 用隔离 fixture 先完成 L1，L3 记 UNPROVEN |
| 测试出现失败 | 保存最小复现，修复后继续全套，不删除失败用例 |
| 版本不一致 | 先修 pin/import path，再做功能结论 |

除非遇到以下真正阻塞，不能停下来询问用户：

- 缺少不可替代的外部凭据且没有安全 fixture；
- 修复会删除或覆盖用户明确未提交的正式数据；
- 两种产品语义都与本手册冲突且无法通过已有规则判断；
- 需要向真实外部系统执行不可逆操作但没有授权。

即便遇到真正阻塞，也要先完成所有不依赖该条件的修复和测试，并在最终报告中列出阻塞项。

## 20. 最终交付标准

本次工作不是“报告发现了问题”，而是要把系统推进到以下状态：

~~~text
已知问题全部复现并分类
    -> 可修复问题全部修复
    -> 每个修复都有回归测试
    -> JobsFlow vendor 使用修复后的 SOP Control
    -> 正式入口真实运行通过
    -> 核心负向测试通过
    -> 成本和 secret 检查通过
    -> 升级/回滚有证据或明确 UNPROVEN
    -> 最终报告给出真实发布级别
~~~

只要 dynamic control 确认仍不能进入 effective rules，或者 JobsFlow 正式 intake 仍然 traceback，就不能报告为完成，也不能报告为达到 8.5 分。

最终报告必须让没有看过前序对话的人，仅凭 commit、命令、输入、输出和证据，就能复现“修复前为什么失败、修复后为什么通过”。
