# SOP Control：活在项目里的可进化确定性空间技术手册

> 版本：2026-08-31  
> 性质：方向性技术手册与存量系统改造蓝图  
> 适用对象：SOP Control 核心开发者、适配器开发者、规则库作者、工作流产品开发者  
> 本文不改变现有代码或权威状态；文中“目标态”“建议新增”均表示后续工程任务，而非当前已经具备的能力。

---

## 0. 摘要

SOP Control 的最终目标，不是写出一段更强的提示词，也不是让模型背下更多注意事项，而是把项目逐步塑造成一个**每个可到达点都可接受的执行空间**：

> 模型应当是在“每个点都可接受的空间”里拥有最大自由的执行者。空间内部自由，空间外部不可到达。设计工作的对象是空间，而不是执行者的心理。

这里真正要消除的不是抽象的“错误空间”，而是**执行时仍需临场猜测的歧义空间**。每当项目把一个原本需要模型推断的问题变成可读取、可执行、可验证的确定事实，模型就少做一次不可靠推理。用户感受到的“模型越来越聪明、越来越坚决”，主要不是模型本身变强，而是项目中已经确定的事实越来越多、合法入口越来越少、反馈越来越靠前。

这个空间必须满足两个方向：

1. **能生长**：从用户纠正、门禁触发、失败修复、生产证据和专家规则中持续吸收新事实。
2. **能修剪**：规则可以撤销、替代、降级、限时、缩小作用域；旧入口可以删除；过时事实可以失效。注册与撤销的成本必须大致对称。

“活在项目里”的含义是：这些确定事实的权威表示、生命周期、证据、作用域和执行入口，都持久化在项目的控制面中；任何新会话、新模型、新平台在开始工作时都从项目恢复同一世界，而不是依赖某个模型记住上次对话。模型上下文只是项目状态的一次**有损投影**，不是记忆本体，更不是权威源。

现有 SOP Control 已经具有正确的骨架：Rule / Evidence / Verdict 三原子、规则注册表、内容寻址证据、任务契约、平台投影、运行时拦截、完成门、语料与变异验证。下一阶段不应推倒重来，而应把这副骨架从“规则可以被登记和执行”推进到“项目能持续学习、主动遗忘，并让任意模型恢复到同一受控空间”。

## 1. 问题重新定义：不是训练模型，而是消除项目中的未决问题

### 1.1 为什么仅靠模型改进无法解决

模型在执行项目任务时，通常同时面对四类不确定性：

- **规范不确定性**：用户到底要求什么，临时偏好与长期规则如何区分；
- **结构不确定性**：正确入口、状态源、依赖关系和完成路径在哪里；
- **历史不确定性**：以前做过什么、为什么这样决定、哪些尝试已经失败；
- **能力不确定性**：当前模型是否能稳定守边界、输出结构化结果、完成验证。

增加提示词只能暂时描述这些问题，不能把它们变成事实。上下文会被截断、稀释、重新概括；模型会更换；不同平台读取不同文件；同一句自然语言在不同任务里也可能有不同含义。要求模型“谨慎”“高效”“先验证”属于倾向塑造，能改善平均表现，却不能证明一次具体执行真的遵守了规则。

因此，SOP Control 不把“模型理解了”当成控制成立，而把下面这条链路是否闭合当成控制成立：

```text
现实或用户表达
    ↓ 观察
候选事实（尚未授权）
    ↓ 澄清与同意
权威事实（带作用域和生命周期）
    ↓ 编译
项目入口、门禁、契约、投影
    ↓ 执行
运行时事件与测试证据
    ↓ 判定
pass / gap / fail / unknown
    ↓ 复查、修复、撤销或替代
新的项目状态
```

### 1.2 “错误空间”与“歧义空间”的区别

“挤压模型犯错的空间”容易把重点放在禁止项上：再加一条规则、再加一句“不要”、再加一道门。更准确的对象是**歧义**：系统尚未决定、执行者不得不猜的地方。

例如：

- “不要写旧入口”仍要求模型识别什么是旧入口；删除旧入口并让所有调用只剩一个入口，则不再需要这次判断。
- “修改后记得运行测试”仍要求模型决定运行哪组测试；把完成动作绑定到确定的验证命令，则不再需要猜。
- “不要直接改控制器状态”仍可能被遗漏；让唯一写入口成为 `sopctl`，并在文件写入前拦截，则违规路径不可到达。

所以新增规则时必须问：

> 这条规则只是告诉模型什么不能做，还是能让这件事以后根本不需要模型决定？

优先级应为：

1. 删除错误入口；
2. 合并重复入口；
3. 用结构和类型表达唯一合法路径；
4. 用工具封装必需步骤；
5. 在边界上拦截；
6. 最后才用文字提醒。

门禁是必要的，但门禁也会误拦、老化并产生自身缺陷。**删除一条多余路径通常强于增加一个守卫**。

### 1.3 结构性错误与判断性错误

应明确两类目标，避免承诺“不再犯任何错”。

**结构性错误**包括越界写入、使用旧入口、漏掉必需字段、跳过验证、读取错误状态源、完成后重复执行。这类问题的合法状态集合有限，应尽可能移出模型的判断范围，使其“不可能发生”或在副作用之前被拒绝。

**判断性错误**包括文案是否自然、需求重点如何排序、一个候选规则是否值得永久化、两个可接受方案哪个更好。这类问题无法完全消除，应通过小步变更、明确证据、廉价复查和可逆决策降低成本。

SOP Control 的强项首先是结构性错误；它不应伪装成替代产品判断的万能系统。

## 2. 核心概念：可进化的确定性空间

### 2.1 确定事实

“确定事实”不是任何写进文件的句子，而是满足以下条件的项目状态：

1. **有身份**：能被稳定 ID 引用；
2. **有来源**：知道由谁、从什么现场、在何时提出；
3. **有作用域**：项目、目录、工作流、任务、平台或时间范围明确；
4. **有权威级别**：候选、已接受、已激活、已监控等状态不能混淆；
5. **有消费者**：知道哪些代码、门禁、投影或工具真正使用它；
6. **有证据**：能证明消费者存在、测试有效、运行时确实决策过；
7. **可失效**：源文件变化、证据过期、作用域结束或用户撤销时，确定性自动下降；
8. **可替代**：新事实可显式 supersede 旧事实，而不是无痕覆盖。

现有 `Rule`、`Evidence`、`Finding`、`Verdict` 已覆盖大部分基础属性。未来不应另造一套平行“项目记忆”，而应围绕三原子扩展生命周期和索引。

### 2.2 可接受空间

设项目在某个时刻的全部可能操作为 `A`，当前权威事实和结构约束允许的操作为 `A_ok`。控制系统的目标不是替模型选出唯一动作，而是保证：

```text
模型可到达的动作集合 A_reachable ⊆ A_ok
```

当存在多个都可接受的实现时，模型仍可自由选择；当某种差异会造成不可接受后果时，这种差异不应继续留给模型临场决定。

这一定义避免两个极端：

- **提示词自由主义**：把所有约束交给模型自觉，空间外仍可到达；
- **流程僵化主义**：把每个细节都固定，连无害的实现自由也消灭。

控制的精度应与风险匹配。低风险格式选择可以自由；生产发布、权限修改、状态源变更必须由结构约束。

### 2.3 空间生长不是规则数量增长

规则越多不代表空间越成熟。成熟度应看：

- 需要模型猜测的关键决策是否减少；
- 规则是否进入了真实消费者；
- 旧入口是否被删除；
- 失败能否产生可复用的新事实；
- 新模型是否能恢复同一状态；
- 规则撤销后投影、门禁和证据是否同步变化。

一条删除旧入口的改动，可能比十条新增警告更能扩大“确定区域”。相反，互相冲突、无人消费、无法撤销的规则会增加歧义。

### 2.4 双向生命周期

空间必须同时有吸收和释放：

```text
观察 → 提议 → 澄清 → 接受 → 编译 → 激活 → 监控
  ↑                                           ↓
重新提出 ← 拒绝         替代 / 降级 / 暂停 / 废弃
```

“能撤销”不是附属功能，而是长期治理成立的前提。只会收紧的系统最终会出现两种结果：规则堆积到无法工作，或用户绕过整个控制器。后一种情况会一次性失去全部治理能力。

撤销不等于删除历史。正确方式是保留旧事实、原因和证据，但使其不再进入当前有效集合，并让所有投影和执行器据此更新。

## 3. “活在项目里”的严格定义

### 3.1 什么叫活在项目里

一个事实只有同时跨过以下七层，才算真正活在项目里：

| 层 | 问题 | 目标态 |
|---|---|---|
| 权威层 | 项目认定的事实是什么？ | 有版本、有 ID、有生命周期的注册记录 |
| 作用域层 | 在哪里、对谁、何时有效？ | 项目/路径/任务/平台/时间边界可计算 |
| 编译层 | 事实怎样变成约束？ | 生成契约、配置、类型、入口或 guard |
| 投影层 | 当前执行者需要知道什么？ | 按任务和风险生成最小充分上下文 |
| 执行层 | 违规是否真的不可到达？ | 工具前拦截、唯一入口、CI 与完成门 |
| 证据层 | 怎么证明它生效？ | 测试、trace、来源哈希、变异验证 |
| 演化层 | 怎么更新、撤销、替代？ | 对称命令、影响分析、原子重投影 |

仅出现在 `AGENTS.md` 的文字属于投影，不是权威本体；仅出现在 registry 但无人消费的规则只是已记录事实；仅有消费者但无证据，不能宣称已经可靠执行。

### 3.2 项目状态与模型上下文的关系

目标关系应是：

```text
项目权威状态
 ├─ 当前规则集合
 ├─ 当前任务契约
 ├─ 当前入口与拓扑
 ├─ 当前模型/执行器风险策略
 ├─ 当前证据与未解决 finding
 └─ 决策历史与撤销关系
        ↓ 按会话、任务、平台编译
最小上下文投影
        ↓
任意模型执行
        ↓ 事件、结果、拒绝、修复
项目权威状态
```

模型上下文具有四个限制：容量有限、会被摘要、无法可靠跨模型、不能证明执行事实。因此上下文只能承担两件事：

1. 告诉模型当前合法动作和必要事实；
2. 告诉模型如何调用控制面。

它不应承担：长期记忆、权威状态、完成证明、规则冲突解决或权限授予。

### 3.3 新会话恢复协议

任何平台适配器启动新会话时，应按固定协议恢复项目，而不是寄希望于模型主动搜索：

1. 定位项目根和控制面版本；
2. 校验权威状态完整性；
3. 读取当前任务及其唯一合法动作；
4. 计算当前有效规则，而不是投影全部历史规则；
5. 读取未解决的高风险 findings 与证据新鲜度；
6. 识别执行器身份；身份未知时采用保守策略；
7. 生成任务相关的最小投影；
8. 在第一次副作用前完成运行时 hook 握手；
9. 将本轮工具调用、拒绝、验证和结果重新写回项目。

恢复结果应可由确定性程序计算。模型不应该先读十份文档再自己推导“现在该做什么”。

### 3.4 项目驻留不等于把所有内容塞进 `.sopcontrol`

“活在项目里”是权威归属，不是单一目录崇拜。合理分工是：

- 业务源码、测试、设计文档继续在普通仓库路径；
- 控制面保存规则身份、关系、状态、证据索引和编译结果；
- 权威规则可引用普通文档的内容哈希，文档变化自动使确认失效；
- 所有控制面写入只经 `sopctl`，避免模型绕过生命周期；
- 可读投影进入平台原生文件，但明确标记为自动生成、非权威。

这样既能版本控制，又不会让控制器复制整个项目。

## 4. 目标架构：一个双环、三平面系统

### 4.1 三个平面

#### A. 权威状态平面

保存项目已经确认的事实及其生命周期：Rule、任务契约、执行器身份、候选事实、例外、替代关系、证据引用。它回答“当前世界是什么”。

要求：确定性、可校验、可迁移、不可被模型直接改写。

#### B. 执行控制平面

把有效事实编译为唯一入口、工具策略、路径权限、完成门、CI 检查和运行时 guard。它回答“哪些动作可到达”。

要求：副作用前执行、默认保守、决策可解释、平台适配器语义一致。

#### C. 观察与学习平面

收集工具事件、重复纠正、修复指纹、门禁拒绝、证据过期、用户反馈和生产结果，形成候选事实。它回答“项目从哪里继续学习”。

要求：检测可以宽，激活必须严；观察不能自动获得授权。

### 4.2 快环与慢环

#### 快环：每次执行都运行

```text
恢复状态 → 生成任务投影 → 检查工具调用 → 记录 trace
→ 验证完成定义 → 产出 Verdict → 更新当前任务
```

快环必须是确定性的，不能调用 LLM 决定权限。

#### 慢环：周期性治理

```text
聚合重复事件 → 形成候选 → 去重与冲突分析 → 用户/专家确认
→ 编译与测试 → 激活 → 观察误拦和绕过 → 修剪或替代
```

慢环可以使用模型帮助归类、摘要和提出方案，但模型输出只能成为 Candidate；接受、权限提升和高影响激活必须走明确同意与证据门。

### 4.3 从“规则”扩展为“确定事实族”

未来可在不破坏三原子的前提下，为 Rule 增加受控类型，而不是建立互不相通的数据库：

- `policy`：用户长期要求，例如禁止直接写控制状态；
- `topology`：唯一入口、状态源、依赖方向；
- `workflow`：步骤顺序、完成定义和回滚路径；
- `capability_policy`：不同证据充足度下的控制旋钮；
- `exception`：有期限、有责任人、有范围的临时豁免；
- `deprecation`：需要删除的旧入口及最后期限；
- `decision`：已经裁定且不应在每个会话重新讨论的设计决定。

分类的目的不是方便展示，而是选择不同的编译器、证据要求和撤销行为。

## 5. 当前代码评估：已经具备什么，还缺什么

### 5.1 已具备的正确骨架

#### Rule / Evidence / Verdict 三原子

`model.py` 已将规则、证据、finding 和判定建模为明确记录；Evidence 有有效期和输入哈希；Verdict 有理由、下一动作和 grounding。这使系统能区分“写过一句话”“存在消费者”“结构化证据证明”“本轮运行时真的执行”。这是项目驻留的基础，不应改回自由文本记忆。

#### 规则注册表与显式生命周期

`registry.py` 通过 `ALLOWED_TRANSITIONS` 拒绝非法迁移，新增规则不能覆盖同 ID 记录，接受前会检查冲突。它已经体现“历史不能无痕覆盖”。

#### 平台投影

`project.py` 从 registry、任务和成熟度生成 `AGENTS.md` / `CLAUDE.md` 小节，标明权威源，并检查投影漂移。它已经实现“权威状态 → 模型上下文”的单向编译雏形。

#### 运行时控制和完成证据

`harness.py` 以稳定 guard ID 决定工具调用；`trace.py` 记录本轮决策并设置七天有效期；`verdict.py` 只在消费者、测试、trace 和确认书条件齐备时给出更高吸收等级。这已经超越“模型自称遵守”。

#### 任务契约

`task.py` 将目标、允许写入范围、必需规则、MUST 字段、修复预算和合法迁移固化。任务状态被投影给新会话，能够阻止旧上下文覆盖新状态和重复执行已交付副作用。

#### 变异验证

`tests/corpus/test_mutations.py` 不把“负向用例没有报警”直接当成功，而是退回修复，要求原本沉默的对照真正变红。这是把经验活在测试中的典型方式：即使换成更弱模型，也不能轻易重犯同一类错误。

### 5.2 当前真实缺口

#### 缺口一：规则生命周期能进入终态，但缺少完整退出通道

模型层已经定义 `superseded` 和 `deprecated`，但它们是终态；CLI 当前只有 add/list/accept/attest，没有面向用户的 transition、supersede、deprecate、reactivate 或 scoped exception 流程。任务的 `blocked` 也是终态，只能另开任务。

这意味着系统“会长不会剪”：内部枚举表达了废弃概念，但实际管理通道不完整。长期运行后，用户很可能绕开控制器。

#### 缺口二：`unknown` 模型画像采取了偏宽策略

`capability.py` 中 `unknown` 当前得到两次修复、目录前缀写入和非严格 schema，接近 strong，而不是保守默认。这与“换模型后不应扩大可达空间”矛盾。未知不是能力强的证据；在中途换模型、平台未传身份、画像过期时会形成 fail-open。

#### 缺口三：能力画像主要来自付费探针，而真实行为没有持续回写

现有三维探针能完成冷启动，但项目每天已经自然产生更有价值的事实：范围越界、缺 MUST 字段、门禁拒绝、修复轮次、格式失败、验证漏跑。当前这些事件没有聚合为持续更新且带置信度的执行器画像。

#### 缺口四：意图检测窄，且候选机制主要依赖固定措辞

`intent.py` 坚持“讨论优先、临时指令不晋升、候选不自动授权”，安全边界正确；但永久规则主要依靠“以后必须”等固定词。用户若通过三次纠正表达稳定偏好，系统仍可能看不见。

这里不应放宽“自动激活”，而应放宽“候选采集”：宁可多收候选，再批量去重和请求确认；不能把宽检测等同于宽授权。

#### 缺口五：重复错误指纹只服务修复熔断，尚未成为学习信号

`Finding.fingerprint` 和 `repair.py` 已能识别同类断口、阻止无限自动修复，但没有把“同一指纹重复出现”升级为规则候选、缺失测试候选、旧入口删除候选或架构问题候选。宝贵行为证据停在任务层，没有回流到空间塑造。

#### 缺口六：投影是全量任务列表加硬规则，尚未按任务做最小充分切片

`project.py` 能保证投影来自权威源，却会把所有任务和所有硬规则放入平台文件。项目增长后，上下文会重新变成稀释的长文。需要从“同步全部事实”升级为“按当前任务、路径、风险和平台编译最小投影”，同时保留可查询入口。

#### 缺口七：规则仍偏向 guard，而删除旧入口尚未成为一等成果

`Rule.legacy_markers` 已可表达旧入口存活风险，这是很好的起点；但当前吸收梯子主要衡量规则是否有消费者、测试和 trace，尚未直接奖励“决策点被删除”。未来应把入口数量、遗留路径清除、单一状态源等作为结构性成果，而不只是又增加一个拦截器。

#### 缺口八：账本混合“历史”和“当前快照”的职责

`ledger.py` 同时支持 append-only 与 `replace_snapshot`。在小规模下可用，但未来要同时回答“现在有效什么”和“为什么变成这样”时，需要明确：事件历史不可变，当前视图可以重建；不能通过替换快照丢失用于学习和撤销分析的历史。

## 6. 存量代码改造方案

本节说明朝目标态修改现有代码的推荐顺序。它不是一次大重构，应拆成能独立验证的小任务。

### 6.1 第一优先级：先补“不会变宽”和“能退出”

#### 6.1.1 将 unknown 改为保守策略

建议语义：

- `unknown` 不代表弱，也不代表强，而代表“尚无扩大权限的证据”；
- 写入粒度至少 `file` 或 `prefer_file`；
- 强制结构化 MUST 字段；
- 修复预算最多 1；
- 高影响动作要求明确身份或人工确认；
- 一旦从项目事件积累足够证据，可自动建议提升，但不能仅凭模型自报提升。

必须新增回归场景：会话中途把 strong 模型换成未知模型，原有项目状态不变，但新模型可达动作集合不能扩大。

#### 6.1.2 建立规则撤销、替代、暂停与缩域通道

建议新增显式 CLI 语义，而不是开放任意 status 写入：

```text
sopctl rule supersede OLD --by NEW --reason ...
sopctl rule deprecate RULE --reason ...
sopctl rule suspend RULE --until ... --reason ...
sopctl rule narrow RULE --scope ... --reason ...
sopctl rule reinstate RULE --reason ...
```

每个动作应：

1. 校验调用者和风险等级；
2. 计算受影响消费者、任务、投影和 guard；
3. 对高影响规则先展示影响计划，再确认执行；
4. 追加生命周期事件，不覆盖历史；
5. 原子刷新所有平台投影；
6. 使旧 trace 不再证明新状态；
7. 运行冲突与 gate 检查；
8. 生成可逆操作或明确不可逆部分。

现有 `superseded` / `deprecated` 可以继续作为历史终态，但“暂停”不应伪装成废弃，建议增加独立状态或生效窗口。旧规则复用时最好创建新修订，而不是篡改终态记录。

#### 6.1.3 为 blocked 任务建立“裁决后续链”，不是重开后失联

`blocked` 保持不可直接复活是合理的，因为旧契约已经证明不足；问题是新任务没有结构化关联。建议增加：

- `resolution_of`：新任务解决哪个 blocked 任务；
- `blocked_reason_code`：范围不足、证据不足、冲突、预算耗尽等；
- `decision_ref`：人工裁决依据；
- `superseded_by_task`：旧任务指向新任务；
- 投影只展示当前可执行链，但保留历史链接。

这样既不允许旧上下文继续执行，又不丢失学习轨迹。

### 6.2 第二优先级：扩大观察，不扩大授权

#### 6.2.1 把 Candidate 变成统一观察入口

保留当前安全原则：任何自动检测只产生 Candidate。扩展候选来源：

- 明确永久措辞；
- 同一偏好的重复纠正；
- 同一 guard 的重复拒绝；
- 同一 finding fingerprint 的多次修复；
- 每次都需要人工补做的验证步骤；
- 已废弃入口持续被调用；
- 多个任务重复出现的相同 `required_field`；
- 外部专家规则包，但仍标记来源和适用范围。

Candidate 建议具有以下字段：

```yaml
candidate_id: CAND-...
kind: policy | topology | workflow | capability_policy | deprecation
statement: ...
sources: [...]
scope_guess: ...
frequency: ...
first_seen_at: ...
last_seen_at: ...
confidence: ...          # 只表示“可能是稳定模式”，不表示已授权
suggested_action: add_rule | delete_entry | add_test | change_tool
conflicts: [...]
status: observed | triaged | rejected | promoted | expired
```

候选可以宽收，但默认不进入 harness、不授予权限、不改变任务契约。

#### 6.2.2 在 gate 触发时采集，而不是事后要求用户复述

门禁触发是最有价值的采集时刻，因为现场同时存在：具体动作、路径、guard、关联规则、模型身份和拒绝理由。此时应自动完成：

1. 记录事件；
2. 聚合稳定指纹；
3. 判断是偶发失误还是重复结构问题；
4. 生成候选修复方向；
5. 在合适时机批量呈现给用户，而不是每次打断。

例如 `GUARD-CONTROLLER-WRITE` 三次阻止不同模型直接写控制目录，更可能说明“合法写入口发现性不足”或“某个平台适配器未暴露 sopctl”，优先建议改善入口，而不是给模型再加一句警告。

#### 6.2.3 把纠正次数变成行为证据

自然语言是否含“以后必须”不应成为唯一依据。建议将纠正事件规范化为：对象、期望动作、实际动作、作用域、是否相同指纹、用户是否撤回。出现稳定重复后只提示一次：

> 项目过去三次把 X 纠正为 Y，是否将其登记为项目规则，或直接删除 X 入口？

用户可以选择：接受为规则、仅当前工作流、添加测试、删除旧入口、忽略或永久拒绝该候选。

### 6.3 第三优先级：让能力策略从真实任务中被动生长

#### 6.3.1 冷启动探针降级为补充手段

三维探针继续用于第一次接入，但长期画像应来自真实执行事件。建议记录可验证特征：

- 允许范围内提交率；
- 路径越界拒绝次数；
- MUST 字段一次完整率；
- 契约接受前的修订次数；
- 修复预算使用情况；
- 验证漏跑次数；
- 输出解析失败率；
- stale 上下文冲突次数；
- 相同错误复发率。

#### 6.3.2 画像不是永久标签，而是带条件的策略证据

不要把模型固定叫作“弱模型”。画像应至少按以下维度分桶：

- 模型与版本；
- harness / 平台；
- 项目；
- 任务类型；
- 时间窗口；
- 观测样本数。

同一模型可能在代码修改上稳定，在长文结构化输出上不稳定。控制旋钮应由相关维度的证据计算，并保留理由。

#### 6.3.3 权限只能证据式放宽，失败应快速收紧

建议采用滞后机制：

- 默认保守；
- 多次真实任务稳定后逐级放宽；
- 一次高风险越界立即收紧；
- 画像过期回到保守，而不是保留旧权限；
- 切换模型或平台重新计算，不继承另一身份的放宽结果。

这里调节的是写入粒度、修复次数、输出 schema 和确认频率，不能提高模型本身的副作用权限。

### 6.4 第四优先级：从全量投影升级为最小充分投影

#### 6.4.1 将投影分为常驻核和任务切片

**常驻核**只包含：

- 权威源和禁止直改规则；
- 当前成熟度及沉默含义；
- 当前任务 ID 与唯一合法动作；
- 如何查询更多信息；
- 完成门与不可绕过原则。

**任务切片**按当前契约计算：

- 与 `allowed_writes` 相交的规则；
- `required_rules`；
- 关联 findings；
- 相关旧入口；
- 本任务验证命令；
- 已完成或 blocked 前序任务的必要摘要；
- 当前执行器的控制旋钮。

其他事实留在权威状态，通过 `sopctl explain` 按需查询，而不是全部注入上下文。

#### 6.4.2 投影必须可追溯

每次投影建议包含：

- 权威状态版本或摘要哈希；
- 生成时间与目标平台；
- 所含规则/任务 ID；
- 为什么包含每一条；
- 刷新命令；
- stale 检测结果。

平台适配器不得自行翻译规则语义，只负责传输同一编译结果。

### 6.5 第五优先级：把“删除决策点”纳入正式成果

为每条高频 guard 增加结构分析：

1. 为什么这个违规入口仍存在？
2. 能否删除、合并或使其不可发现？
3. 能否由唯一工具自动完成合法动作？
4. 如果必须保留，guard 的误拦和绕过证据是什么？

建议增加两类 finding：

- `redundant_entry_point`：同一意图存在多个入口，其中部分绕过控制；
- `decision_should_be_compiled`：多个任务重复让模型做同一个可确定决定。

吸收报告中除“规则已 enforced”外，还应报告：

- 删除了多少旧入口；
- 减少了多少模型决策点；
- 哪些 guard 因结构修复而可以移除；
- 是否仍存在平行状态源。

### 6.6 第六优先级：分离事件历史与当前物化视图

推荐目标：

- **事件日志**：只追加，保存观察、候选、接受、激活、拒绝、撤销、工具决策、验证和任务迁移；
- **物化视图**：registry、当前任务、当前画像、当前未解决 findings，可从事件重建；
- **大型原始证据**：按内容寻址保存或引用，不重复塞入日志；
- **压缩**：可以生成快照，但快照必须带来源事件区间和哈希，不能抹掉审计链。

这使“项目为何变成现在这样”可回答，也让撤销影响分析有可靠输入。

## 7. 未来代码如何沿这个方向进化

### 7.1 每个新功能先回答五个问题

任何新模块、适配器或规则类型进入主干前，应回答：

1. 它消除了哪个原本需要模型猜测的问题？
2. 权威事实存在哪里，模型上下文是否只是一份投影？
3. 哪个生产消费者实际使用它？
4. 如何证明它不仅存在，而且本轮真的生效？
5. 用户如何撤销、替代或缩小它？

若只能回答“我们会在提示词里提醒模型”，说明还没有完成空间塑造。

### 7.2 最差模型验收法

长期验收标准不是“最强模型能不能成功”，而是：

> 换成能力更弱、上下文更短、没有历史记忆的模型，结构性结果会不会改变？

具体测试：

- 不知道项目历史的模型能否找到唯一入口；
- 忽略文字提醒时，越界副作用是否仍被阻止；
- 不会主动运行测试时，任务是否无法进入 delivered；
- 中途换模型时，新模型是否读取当前任务而非重复旧副作用；
- 输出啰嗦或格式不稳时，结构化边界是否收紧；
- 模型自称完成但没有 E4 证据时，Verdict 是否拒绝 pass/enforced。

### 7.3 经验必须固化为机器可证伪资产

每次发现真实缺陷，应选择最合适的固化层：

- 入口问题 → 删除或统一入口；
- 边界问题 → runtime guard；
- 数据契约问题 → schema / 类型；
- 回归问题 → 测试；
- 检测器盲区 → corpus + mutation；
- 用户稳定偏好 → Candidate，经同意后成为 Rule；
- 一次性任务要求 → Contract，不进入永久规则；
- 设计裁决 → 可引用的 decision fact，不在每次会话重诉。

只写总结而没有可证伪资产，经验仍主要活在人的记忆里。

### 7.4 新规则必须带“退出设计”

新增规则时同时定义：

- 失效条件；
- 作用域；
- 责任人；
- 复查时间；
- supersede 关系；
- 撤销影响；
- 哪些 guard / 测试 / 投影将随之移除；
- 是否可由更强结构替代。

没有退出设计的规则默认只能停留在 proposed，不能进入长期 monitored。

### 7.5 平台适配器必须薄

Codex、OpenCode、Gemini、Cursor 或未来平台只应负责：

- 定位项目；
- 获取控制器编译后的投影；
- 在工具调用前传递标准 payload；
- 执行统一决策；
- 回写事件；
- 处理平台特定 I/O。

规则语义、权限判断、生命周期和证据判定必须留在零 LLM 的脊柱。否则每增加一个平台，就复制一套可能漂移的治理逻辑。

### 7.6 规则包应是可审查的起始空间，不是默认真理

第三方专家可以提供某类工作流的预设空间，例如求职、财务报告、部署或安全审查。但规则包必须：

- 声明领域、版本和来源；
- 默认以 proposed 或 recommended 导入；
- 显示与项目现有事实的冲突；
- 允许逐条或分组接受；
- 不自动获得项目权限；
- 可整体升级、回滚和卸载；
- 项目本地覆盖必须显式记录。

这使 SOP Control 可以通用于不同 workflow，而不是预装一个庞大、僵硬的万能规则库。

## 8. 端到端运行示例

### 8.1 用户通过重复纠正形成规则

1. 模型第一次修改旧入口，用户纠正到新入口；系统记录 correction fingerprint。
2. 第二个任务再次发生，系统聚合相同对象与期望动作。
3. 第三次发生时生成 Candidate，但不自动拦截。
4. 系统向用户批量建议：“删除旧入口”优先于“新增禁止规则”。
5. 用户同意删除；任务契约限定修改范围和完成定义。
6. 删除旧入口，新增跨领域 corpus 与 mutation，证明检测器能看见回退。
7. 若仍需兼容窗口，则 guard 暂时存在并带失效日期。
8. 兼容窗口结束后移除 guard；项目少了一个决策点。

最终学到的不是一句“模型以后注意”，而是旧入口消失、回退会让测试变红。

### 8.2 会话中途更换模型

1. 旧模型的任务状态和所有工具事件已经写回项目。
2. 新模型启动时不继承旧模型画像，也不依赖旧对话摘要。
3. 恢复协议读取当前任务 revision、合法动作和权威状态版本。
4. 身份未知，控制旋钮采用保守值；可达空间不会扩大。
5. 投影指出哪些副作用已完成，防止重复执行。
6. 新模型提交后，项目根据真实事件更新该身份的画像。

这里没有昂贵的重新探测要求；真实任务本身就是持续探针。

### 8.3 撤销一条已经 enforced 的规则

1. 用户请求废弃规则，控制器先展示影响：关联 guard、投影、任务、测试和风险。
2. 高影响操作要求第二阶段确认。
3. 追加 deprecate/supersede 事件，不修改旧历史。
4. 从当前有效集合移除旧规则，原子刷新投影。
5. 旧 trace 仍保留，但不能证明新状态。
6. 若 guard 只服务该规则，产生删除 guard 的后续任务；若仍被其他规则引用则保留。
7. 运行 gate 和反向测试，确保撤销后既不残留假约束，也不意外开放无关权限。

撤销成本不应远高于登记成本，否则用户最终会绕过系统。

## 9. 迁移路线

### 阶段 A：封住当前语义漏洞

目标：换模型不会变宽，规则和任务有可追踪的退出路径。

1. 将 `unknown` 画像改为保守旋钮；
2. 增加模型切换与画像过期测试；
3. 为 rule 增加 supersede / deprecate 的正式 CLI；
4. 为 blocked 任务增加 resolution 链；
5. 明确暂停、限时例外和缩域的数据模型。

完成标准：任何身份丢失、规则撤销或人工裁决都不会依赖手改控制文件；当前空间可计算且不因未知而扩大。

### 阶段 B：建立观察到候选的学习环

目标：用户无需刻意使用“以后必须”才能让系统发现稳定模式。

1. 统一 Candidate schema；
2. 接入 guard 拒绝、finding 指纹、用户纠正和任务失败；
3. 做频率聚合、去重、作用域推断和冲突提示；
4. 提供批量 triage；
5. 守住“候选不等于授权”的宪法测试。

完成标准：重复结构问题能自动浮现，但未经同意不会改变 harness 或权限。

### 阶段 C：能力画像被动化

目标：探针只解决冷启动，日常策略来自真实项目证据。

1. 定义行为事件 schema；
2. 按模型/平台/项目/任务类型聚合；
3. 建立保守默认、渐进放宽、快速收紧和过期机制；
4. 在 projection 和 task open 中使用相关画像；
5. 校验画像只能调控制强度，不能授予副作用权限。

完成标准：中途换模型无需重新跑整套探针，且未知身份不能继承旧模型的宽松策略。

### 阶段 D：最小投影与确定性恢复

目标：项目增长后，上下文仍短且无歧义。

1. 定义新会话恢复协议；
2. 将投影拆为常驻核与任务切片；
3. 增加状态摘要哈希和包含理由；
4. 平台适配器统一使用同一编译接口；
5. 用长历史、多任务、换平台语料验证。

完成标准：新模型无需读完整历史就能说出当前唯一合法动作，投影 stale 会被 gate 发现。

### 阶段 E：删除优先与结构成熟度

目标：从“更多 guard”进化到“更少决策点”。

1. 建立入口与状态源清单；
2. 检测平行入口、遗留标记和重复决策；
3. 把删除入口纳入任务和吸收指标；
4. 当结构保证已足够时移除冗余 guard；
5. 用 mutation 证明旧入口恢复会被发现。

完成标准：控制成熟度提升伴随入口减少，而不是只伴随规则和提示词增长。

### 阶段 F：事件历史与可重建视图

目标：项目能回答“为何如此”，并可靠完成撤销和迁移。

1. 定义统一事件信封和 schema version；
2. 将 registry、任务、画像作为可重建视图；
3. 建立快照、压缩和完整性校验；
4. 提供 dry-run 的影响分析；
5. 验证从事件日志重建当前状态的一致性。

完成标准：当前状态可重建、历史不可无痕篡改、撤销影响可在执行前计算。

## 10. 测试与验收体系

### 10.1 宪法测试

应长期守卫：

- 判定器零 I/O；
- 权威写入只能经控制器命令；
- Candidate 永不直接激活；
- `unknown` 不得比已知弱画像更宽；
- 模型自报不能生成 E4；
- 终态记录不能无痕覆盖；
- 规则撤销必须使投影和消费者同步；
- 平台适配器不能重写规则语义。

### 10.2 生命周期属性测试

适合使用状态机或属性测试验证：

- 所有允许迁移都有逆向治理路径或明确不可逆理由；
- 非法迁移恒被拒绝；
- supersede 后任一时刻最多一个冲突规则有效；
- 暂停到期后状态可确定；
- 任意操作序列后 current view 可由事件重建；
- 重复执行同一命令幂等；
- 崩溃不会留下“registry 已变、projection 未变”的半状态。

### 10.3 跨模型降级测试

至少建立三类执行器夹具：稳定、脆弱、未知。对同一任务比较：

- 最终结构性结果是否一致；
- 未知执行器的动作集合是否更窄或相等；
- 弱执行器是否需要更多引导但不能造成更多不可逆副作用；
- 换模型后是否重复已完成动作。

### 10.4 撤销与修剪测试

每个新增规则类型必须测试：

- 接受后消费者生效；
- 撤销后消费者失效；
- 旧证据不误证新状态；
- 投影不残留；
- 相关任务如何处理；
- 历史仍可解释；
- 恢复规则是否需要新修订。

### 10.5 变异验证继续作为底线

任何新的“没有报警”对照都必须有变异能让它变红。尤其需要增加：

- 未知画像错误继承强画像；
- 被废弃规则仍进入投影；
- revoked guard 仍拦截；
- Candidate 未经同意直接激活；
- 重复纠正未被聚合；
- 删除的旧入口被恢复；
- 新模型重复 delivered 副作用。

## 11. 度量：判断空间是否真的在变好

不以规则总数、文档字数或“模型说理解了”为成功指标。建议度量：

### 11.1 空间确定性

- 高风险任务中需要模型临场选择的结构性决策点数量；
- 单一入口覆盖率；
- 平行状态源数量；
- 投影中规则与实际消费者一致率；
- unknown 状态下的 fail-open 数量。

### 11.2 学习效率

- 重复纠正到 Candidate 的中位次数；
- Candidate 到接受/拒绝的周期；
- 同一 finding fingerprint 复发率；
- 一次修复后被 mutation 永久守卫的比例；
- 通过删除入口解决的问题占比。

### 11.3 可逆性

- 规则登记与撤销的操作步骤比；
- 有退出设计的 active 规则比例；
- 撤销后残留投影/guard/任务引用数量；
- 过期例外按时关闭率；
- 被绕过控制器的事件数量。

### 11.4 跨模型稳定性

- 不同能力模型在结构性结果上的差异率；
- 会话中途换模型后的重复副作用率；
- 未知画像导致的越界率；
- 弱模型完成同一任务所需额外交互量，但不把 token 数直接等同于质量。

### 11.5 诚实度原则

没有真实生产分母、样本太少或没有 E4 时，应标记 `unmeasurable`，不能填 0。无法测量本身就是产品缺口，不是可以隐藏的好成绩。

## 12. 风险与取舍

### 12.1 规则僵化

风险：历史规则长期堆积，项目为了过去的事故牺牲现在的速度。  
对策：生效窗口、责任人、复查日期、撤销通道、入口删除优先、按任务最小投影。

### 12.2 门禁误拦

风险：用户为了工作绕开整个系统。  
对策：决策必须带理由和下一动作；允许有审计的临时例外；统计误拦；优先修结构而不是永久增加 guard。

### 12.3 控制器自身缺陷

风险：确定性代码也会有 case-fold、stale、解析边等有限错误。  
对策：结构化传感器、跨领域语料、mutation、纯函数边界、内容寻址、真实 trace。确定性层的错误类别有限，可被逐步穷尽，投资会复利。

### 12.4 观察变成监控负担

风险：事件过多、隐私泄露、项目膨胀。  
对策：只记录控制所需的结构字段；敏感正文摘要或哈希化；上界和保留策略；候选批处理；项目本地优先。

### 12.5 过度建模

风险：为了统一一切而发明庞大本体，反而增加决策点。  
对策：继续坚持最小骨干；只有真实重复问题证明需要时才增加事实类型；每个扩展必须有消费者、证据和退出设计。

---

## 13. 不做什么

SOP Control 不应：

- 用一个全局 daemon 接管所有项目；项目是权威边界；
- 让 LLM 位于权限判定的关键路径；
- 自动把用户每次纠正永久化；
- 通过模型评分替代运行时控制；
- 为所有 workflow 预装同一套庞大规则；
- 把平台适配器做成第二套控制器；
- 以增加提示词长度作为主要进展；
- 只允许收紧而不允许撤销；
- 因为控制器确定性就假设它不会出错；
- 把 token 少等同于结果好。真正的节能来自减少重复推理和返工。

## 14. 工程决策清单

实现任何相关改动前，用以下清单评审：

### 构想一致性

- [ ] 该改动减少了一个歧义，而不只是增加一句警告。
- [ ] 它保留可接受实现的自由，没有无故固定细节。
- [ ] 更弱模型进入后，结构性结果不会变差。

### 项目驻留

- [ ] 权威事实不依赖当前会话或模型记忆。
- [ ] 状态有 ID、来源、作用域、版本和生命周期。
- [ ] 投影可以从权威源重新生成并检测 stale。
- [ ] 执行事件和完成证据会回写项目。

### 控制成立

- [ ] 有真实生产消费者，而非只存在于文档。
- [ ] 副作用前有检查，而非只做事后审计。
- [ ] 测试能证明检测器真的看见了目标。
- [ ] 自报不能替代 trace 或测试。

### 可进化性

- [ ] 自动观察只生成 Candidate，不自动授权。
- [ ] 新规则有退出、替代和缩域设计。
- [ ] 优先评估能否删除旧入口。
- [ ] 历史保留但不污染当前有效集合。

### 运行成本

- [ ] 日常真实任务尽可能兼任能力观测，不重复烧探针成本。
- [ ] 投影是最小充分信息，而不是全量历史。
- [ ] 失败在副作用前暴露，修复有界。

## 15. 最终判断标准

SOP Control 是否实现了“活在项目里”，不看模型能复述多少规则，而看以下现场：

1. 清空对话，换一个模型，它仍能恢复当前任务和唯一合法动作；
2. 换成更弱模型，项目可能变慢，但不会扩大不可接受副作用；
3. 用户不使用特定咒语，重复纠正仍能被识别为候选；
4. 未经同意，候选永远不会成为权限或硬门；
5. 一条规则被接受后，能找到其消费者、测试、运行证据和来源；
6. 一条规则被撤销后，能证明投影、guard 和当前判定同步退出；
7. 同一种错误发生并修复后，回退修复会让 mutation 变红；
8. 项目随时间增长的不是提示词，而是已确定事实、唯一入口和可证伪资产；
9. 规则数量可以下降，而控制成熟度仍然上升；
10. 用户感到模型“更坚决”，是因为无意义的选择减少，而不是系统逼模型表现得更自信。

归根结底，SOP Control 要建立的不是一个更会劝模型的规则手册，而是一种项目结构：

> 已经决定的事情，由项目记住、编译、执行和证明；尚未决定的事情，模型可以自由探索；需要改变的事情，用户能够低成本撤销。模型可以更换，平台可以更换，会话可以消失，但项目不会失忆。
