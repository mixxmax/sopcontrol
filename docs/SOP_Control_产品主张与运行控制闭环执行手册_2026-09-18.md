# SOP Control 产品主张与运行控制闭环执行手册

> 交给没有参与过本项目的执行模型。编写日期：2026-09-18。基线以开始执行时仓库实际 HEAD 为准；写稿时为 `bc2bcf1` / v0.4.0。此文件是实施与验收契约，不是“已经完成”的声明。

## 0. 一页决策：要修什么，不要改成什么

SOP Control 是一个**项目内、模型中立、低开销的规则控制平面**，面向合作型 Agent 与可提供正式入口的宿主产品。它不是 OS 沙箱、通用 DLP、业务事实判断器，也不因当前控制尚未闭环就改定位为“纯审计器”。实效性审计是证明控制确实发生、发现尚未接通规则的必要反馈能力，不是控制的替代品。

本轮目标：让已确认的项目规则和动态 SOP 在明确的适用入口影响**实际下一步**，让自然逻辑在宿主提供足够前置条件时防止明显无谓工作；同时把公开主张、发布门禁、日志证据强度与真实能力对齐。第一性测试不是“新增多少命令”，而是另一模型换会话后是否仍按用户确定的规则完成任务。

三类平级、长期存在的规则不得被重定义为硬／软／临时层级：

1. 产品本体规则：产品设计形成的入口、状态、写入、必需检查和完成条件。
2. 动态 SOP：用户工作中表达、确认希望长期保留的细致要求；“动态”不等于 TTL，未激活不等于过期。允许范围、下上限、禁止扩大目标和停止／修正条件是规则的一部分。
3. 自然逻辑：无明确反向目的时最小充分、少做无用功的默认计划；用户显式反向要求允许成为本次例外。

**禁止扩大任务**：不自造 Rego/Cedar 竞争品，不引入 daemon、团队服务端或 eBPF，不把每次工具调用交给另一个模型审查，不强推所有只读动作领票，不代替宿主做 JD／材料事实判断，不为追求命令数指标而删除已有用户接口，不未经批准重写公开 Git 历史或修改 JobsFlow 业务语义。

**A 的验收**：当前 HEAD 的完整 CI 矩阵绿；首页所有状态均可由自动证据还原；在未真实验证平台上运行 `compat` 不出现 `verified=true`；支持矩阵每个支持等级有对应测试、探针或明确 UNPROVEN 标签。

### A2. 修首次安装失败路径

`sopctl init` 遇到残缺 `.sopcontrol` 不能因为目录存在就声称初始化完成；用幂等布局验证与受控修复恢复缺失文件，避免覆盖现有规则和账本。优先复用 `init` 或 `doctor` 的修复入口；若新增命令，避免与现有任务修复命令混名。分别验证全新、已完整、仅存在子目录、配置损坏、权限不足；不能“修复”损坏历史为看似正常的空文件。CLI 位置参数绑定（报告中 `logic plan --freeze <path>` 和 `task rebind ... <path>`）按项目既定语法回归，不能为过测试而更改稳定接口。

**A2 验收**：残缺布局有可执行的下一步且可保留数据恢复；CLI 常用路径在支持的 Python 矩阵通过；失败无 traceback、无悄悄清空控制数据。

## 3. 工作包 B：把永久规则接到真实运行入口（本轮核心）

不要以“让任意自然语言句子直接执行”为目标。必须先根据规则能力分层，且在 receipt 中诚实呈现：

| 规则效果 | 谁判定 | 实际动作 |
| :--- | :--- | :--- |
| 可确定性判定的状态、范围、顺序和前置条件 | SOP Control 本地规则选择和 gate | allow / deny / needs_user / unknown；适用规则 ID 必须出现在决策和日志中 |
| 宿主产品定义的事实、JD 贴合、语义审计 | 宿主业务检查器 | SOP Control 验证检查按规则要求发生，结果绑定对象／运行并被下一动作消费；不对语义内容做假阳性裁决 |
| 暂不能机器判定的用户偏好 | 显式标记无消费者／缺适配器 | 不得冒充 enforceable；高影响写入在缺必要证明时停于 needs_user / gap，普通只读按策略观察并报告 |

### B1. 统一“规则选择→动作决策”的接口

在当前 Registry、`dynamic_sop.select_rules`、任务契约／`control_result`、`action_plane.evaluate_payload`、`bridge` 及宿主 gateway 之间设计**一个可追踪的选择与评估入口**：输入有项目、任务、动作／phase、目标对象、actor、现行规则版本和宿主提供的受控检查证明；输出有适用／未适用及理由、必需前置、未知项、决策、下一动作和本次证据标识。保持纯函数／热路径零 LLM，必要的 I/O 在边界调用方进行。多个子系统可共享已编译计划，但不得在运行时重新猜规则含义。

不能把 `rule add --guard-id` 固定在八个字符串就误称“所有已登记规则自动执法”。可保留稳定的内置 guard 作为公共不变量；其他已确认规则须明确绑定一种**已有可执行效果类型**（状态/范围/依赖/宿主检查/受控入口等）与真实消费者。新效果类型需要显式适配器和负向测试；不能悄悄默认 PASS。旧 Registry 数据需要兼容迁移或明确保留“已登记但未接线”状态，不得静默降低控制强度。

“平级”指三类规则都可长期保存、都有可追溯权威，不表示冲突时可以任意覆盖。规则之间若同一对象、时间和动作上产生冲突，先按已确认的作用域与适用条件求交；仍冲突则输出具体冲突和需要用户决定的两种结果，不让 Agent 自行以“动态比本体低”或“自然逻辑最优”为由悄悄改写任何一类长期规则。

### B2. 动态 SOP 的端到端路径

默认无感观察和显式 `learn` 必须继续并存；两者只生成候选。真实用户确认后长期保存、不隐式 TTL，换会话／换模型／重启后仍可由 action context 选中；`once_only`、`defer`、`reject`、`document` 不得被误晋升。若需模型提炼对话，仅走可选低频冷路径，只产出可审提案；当前确定性抽取器不能被宣传成具备一般语义理解、自动扫描每段聊天。无宿主对话事件接线时应显示 `not_connected`，而非承诺“随口说必然记住”。

**贯穿用例**：用户要求“独立审计仅核对 JD 贴合、明显事实问题与指定 LLMO；不要扩展审查、不要为可解释的小问题反复审计”。先确认并编译为长期动态 SOP，再由宿主审计动作携带必需检查结果和次数等证明；SOP 验证必需步骤／目标／轮次，既不替宿主判断 JD 内容，也不无视用户指定的宽严与停止条件。正例、缺检查、错误对象、过度扩审、重复轮次、已解除一次性例外、跨会话／换模型，都要有实测。

### B3. 自然逻辑作为默认而非绝对命令

宿主提供目标、输入集合、已处理集合、算子依赖、成本信息；在信息充分时先做子集过滤，再做昂贵评分／验证。明确的反向实验形成**本次例外**，不污染永久规则。缺少足够语义时返回 `unknown`，不要凭模型猜想拒绝合法计划。用“最近一周目标岗位 → 排除已入表 → 只给剩余岗位评分”的一正一反两条路径验收；要有可复算的调用数、处理范围、延迟或成本对照。

**B 的完成定义**：已确认规则在另一次会话的适用动作中留下 `selected rule -> gate decision -> 宿主运行/阻断 -> evidence` 的同一标识链；没有消费者的规则被报告为 GAP，而非 merely registered 即通过；宿主结果被消费，不只是某处打印“check passed”。

## 4. 工作包 C：合作型 Agent 的入口和权限边界加固

### C1. 先做负向测试，再加固

基于报告逐条复现已知族：shell 引号拆分／拼接、相对路径和链接、Git 的绝对路径与 `-c core.hooksPath`、直接编辑 `.git/hooks`、`.sopcontrol-local` 中可改变绑定的敏感文件、未知 MCP／工具、缺 command／target、畸形任务记录导致的空身份。记录确切入口、当前判定和真实副作用是否发生；**测试只在隔离项目中执行，不对正式仓库写入绕过载荷**。将每个复现变成最小负向回归测试；不能仅在字符串列表上加更多特例。

### C2. 按风险分类处理未知和解析失败

已有 `worktree.resolves_inside` 等路径工具可复用，但不要对所有可能路径套不合适的同一解析函数：区分 Git 元数据、控制器权威状态、可执行 hook／binding 等关键本地状态、普通工作文件。对于列入受控范围的**写动作**，若目标、工具类别、解析或身份状态无法确定，拒绝或请求明确下一步，且说明理由；对于未知**只读动作**可观察、保留未知，不要一律重票或阻断。对于 shell 嵌套执行，仅靠 shlex／AST 和关键词不可能解析任意语言：覆盖可识别的常见变体，对无法归类的高风险动作要求通过正式 wrapper／受控入口，且在文档中明确合作型边界。CI／远端分支保护可提供独立于本地 hook 的发布门；不要把本地 pre-push 描述为不可绕过。

`TaskStore.list_all()` 出错不得被吞掉并改成“无绑定执行者”；解析失败路径必须保留守卫（fail closed for governed writes）。陌生工具至少产生带 `unknown/observe` 的可追踪事件；如果宿主声称该工具属于受控写入口，则不得 observe→allow。OpenCode、Claude、Codex 分别验收实际能力，不能拿一个 harness 的 live 证据代替另一个。

### C3. 人工确认不得由 Agent 自己完成

`rule add --status accepted`、accept、suspend、retire、supersede、范围放宽、移除接线都视为会改变永久权威的动作。预览 ID 只证明“这次预览是什么”，不证明“用户同意”。统一进入可信确认通道：确认凭据只能由 Agent 无法访问／代领的用户侧签发，并绑定规则 ID、变更内容摘要、项目、用途、失效期限和一次性使用；CLI 的 `--by user` 不能铸造身份。现有 ticket 机制可复用其绑定与消费方式，**单靠 TTY 或把 secret 打到模型可见 stdout 仍不构成真实人工确认**。给出不支持可信用户通道的宿主时的显式 `needs_user` 和可操作指引；保持非交互 CI／迁移流程可通过独立、受控的维护者凭据运行，而不是关闭保护。

### C4. 证据语义和并发

账本现有内容摘要只能发现某些损坏／不一致，不可宣称抵抗能写账本者伪造自洽记录；哈希链如果没有外部锚也不等于强防篡改。把 CLI 的“篡改”描述调整成与实际可证明性质一致，并区分 `admitted`、`started`、`completed`、`verified`。日志不因 gate 放行就计执行成功；从宿主回执或独立验证得到完成证据。检查动态规则确认／编译的 load→check→save 竞争，使用同一锁保护整个事务，保留旧 revision 冲突并发测试，不让后确认覆盖先确认。日志／secret 脱敏与异常降级至少用一组对抗用例验证。

**C 的完成定义**：报告所列的常见合作型绕过已变成回归测试且高影响动作被拒或需明确确认；无法保证的深层混淆执行列为边界而非声称已经彻底修复；真实用户拒绝、重复授权、错规则、错 digest、跨项目／旧版本均不得放宽规则。

## 5. 工作包 D：接入、控制覆盖和宿主实效验收

将 `surface inventory` 与真实执行事实关联，逐项标记 discovered、mapped、probed、governed、waived、blocked、gap、unknown；分母必须来源于宿主能枚举的 eligible 执行入口，而不是“本次只有一个动作经过 gate，所以 100%”。无法枚举分母就报告 partial/unknown。覆盖率需同时显示按入口和按本次 run 的结果，区分“配置接通”和“这次真的经过 gate”。

接入中途项目时，`attach` 不应改写产品业务逻辑或覆写第三方 hook；验证真正的入口、detach 保留他人资产。升级时先查版本绑定、语义 diff、动态 SOP 完整保留、适配器兼容、影子测试、原子切换与可回滚；宿主 vendored 副本不会随上游更新自动变化，需由宿主维护的 vendor/pin/manifest 更新通道显式跟进。

至少使用两种宿主形态：

1. 隔离的通用 fixture：可重复跑 CLI、hook、worker／API 与写入口的成功／拒绝／gap。
2. JobsFlow 的**独立隔离副本**：按它自己的正式 CLI／gateway 流程走 read-only scan／筛选／评分／预览／写入和一条动态审计规则。不要修改 JobsFlow 事实校验器或业务标准；若必须改薄适配器，在 JobsFlow 工作流另列明确 diff 和 pin 升级步骤，并报告未获授权时无法完成的部分。

验收必须让另一模型在新会话中跑：一条用户纠正经确认后长期生效；一条自然逻辑节省昂贵步骤；一条高影响写动作缺条件被阻断、条件满足后仅一次兑换并完成。报告用户真实耗时、额外调用、token／模型调用（控制热路径应为零 LLM）、受控单元分子分母、未知项、原始可定位回执。不能用测试 fixture 的自报 success 替代宿主实际副作用。

## 6. 工作包 E：文档、仓库卫生与发布边界

更新 README 中文首页、英文段落和独立中文 README，术语与证据等级一致；头图不改。首页前屏解释“三类永久规则 + 低摩擦接入 + 可证明生效”，并给一个真运行示例；日志和审计作为证明手段，不把产品整体改成纯审计器。用户口头经验的自动提炼能力应准确区分：宿主已接入的事件观察、确定性提取、可选但未接入的真模型、用户真实确认。支持矩阵每格注明事前／事后／投影，不借别的平台演习背书。同步 `LIMITATIONS.md`、`RESIDUAL_RISKS.md`、`PUBLISH.md`、`CHANGELOG.md` 中已复现的绕过与缺口，明确剩余风险。

做仓库卫生审计：确定 `.sopcontrol` 自举的哪些规则、证据和任务是可公开的产品示例，哪些为运行态、个人数据或内部资料；停止继续把无意发布的生成证据提交进去。**不应简单将整个 `.sopcontrol` 忽略**，否则丢失项目内权威；也不应未经用户明确批准重写历史删除 JobsFlow 名称或 Prompt 文件。发现真实秘密／敏感客户信息时停止进一步公开并提出具体授权选择；通常先归档文档和过滤未来提交，历史改写另案处理。

## 7. 建议提交序列与门槛

为便于回滚，各提交尽量小而可运行；不是死板的固定提交数：

1. 基线与失败重现测试；不改变现有判断。
2. CI／CLI／平台证据修复及文档徽章止血。
3. 规则效果类型、选择接口、旧数据兼容和纯函数测试。
4. 动态 SOP 与任务契约接入一个正式 gateway；双向日志／receipt。
5. 自然逻辑默认和一次性反向例外的宿主契约。
6. 入口解析、未知工具、缺字段与 identity 负向回归。
7. 规则变更可信确认与并发事务。
8. surface 覆盖、升级／回滚和隔离宿主演练。
9. 双语文档、限制、发布检查收口。

每一提交必须针对其修改范围跑定向正反例、ruff、`git diff --check`；阶段边界跑完整测试与 `sopctl gate`。若项目 `sopctl gate` 会落正式证据，不要把这些检查副作用偷偷混入代码提交；通过正规 `sopctl` 路径维护证据并清楚报告工作区状态。不要以提交数替代闭环证据。

## 8. 最终验收矩阵：必须同时满足

| 场景 | 正向证据 | 负向证据 |
| :--- | :--- | :--- |
| 三类规则 | 同一适用动作选中正确类型、作用域和证据 | 不适用不误激活；动态长期规则不因时间／重启隐式失效 |
| learn 双入口 | 自动候选／显式 review 同一确认链，长期规则新会话生效 | 闲聊、系统错误、once_only、自称 user、重复提案不进入永久库 |
| 实际执行 | 规则改变下一动作；真实宿主 receipt 可追溯 | 没有消费者、必要检查缺失、gate allow 但未执行，均不报 verified success |
| 自然逻辑 | 先筛未入表、只对剩余评分，少做可量化 | 显式反向实验可执行，不污染永久默认；信息不足不假装知道 |
| 入口安全 | 常用 shell/path/Git 变体和受控写入口被恰当处理 | 未知高风险写、缺字段、身份解析失败不静默放行；安全只读不泛阻断 |
| 权威变更 | 用户侧凭据一次性绑定变更 | Agent 取 preview 自回传、伪造 `--by`、重放、跨项目凭据全部无效 |
| 发布 | 3.10/3.11/3.12 CI 和 gate 绿；README 徽章、平台矩阵可复算 | 无证据平台／harness 不显示 live verified；红 CI 不建议 tag |
| 产品接入 | fixture + JobsFlow 隔离运行可数分母和被控单元 | 未接通／仅映射／未运行均不可计作 governed；升级失败保留旧规则 |

完整技术门包括：干净 venv 安装和版本一致性、全量 pytest + 当前覆盖门（不可降低）、ruff、投影检查、门禁、退出码、兼容性、日志脱敏、并发负测和升级／回滚。对无法复现的报告项标 `not reproduced` 并注明环境与重现命令；对有代码但没有真实宿主证据的项标 `UNPROVEN`，不许改写为 PASS。

## 9. 必须提交的最终报告格式

1. 当前 HEAD／分支／工作区差异，是否 commit／push；每个仓库单独报告，不能把隔离副本冒充正式树。
2. 本手册每个工作包 A–E 的 `PASS / PARTIAL / FAIL / UNPROVEN`、受影响文件及可复现命令。
3. 已知 F 类问题的复现／修复对照：哪项属产品缺口、哪项只是诚实边界；修复前后负向测试名。
4. 三类规则各一条端到端演练：原始用户要求、确认来源、适用上下文、实际动作、下一步变化、可信回执、成本。
5. CI 全矩阵链接／本地解释器、测试与 coverage 数据、完整 gate 状态，不能只报告定向用例。
6. 宿主覆盖的分母、分子和 unknown；JobsFlow 副本的位置及真实 pin，是否需要宿主侧变更。
7. 仍不能证明的路径、平台与对抗边界，用户下一步最小操作。未获用户授权的 push、tag、历史改写不得自行实施。

**发布判定**：只有产品关键链（永久规则真实影响运行、不能自批准解除、成本可接受、宿主证据可追溯）与工程发布门同时成立，才能建议公开 Beta。GA 与跨宿主普适性仍需独立证据；不通过时如实输出阻断，不得用评分或未来计划代替。

## 10. 可直接发送给执行模型的开工指令

> 以本手册为唯一实施范围，在正式 SOP Control 仓库读取当前状态和项目说明后，从工作包 A 到 E 分批实现、提交定向测试、运行完整验收。不要仅重述手册，也不要以已存在的旧报告当新证据。每个问题先写最小复现，再修改生产路径；先保持产品定位和三类规则的长期地位，再完成运行接线、可信确认和宿主验证。保持用户现有脏改，不直接读写 `.sopcontrol/`；对 JobsFlow 仅在隔离副本做验证，需改正式业务产品时先给出最小接口变更并等待授权。不要未经授权 commit、push、tag 或改写历史。每阶段给出事实、diff、测试与仍未证明的项目，最后按第 9 节报告；如果无法取得真实的人类确认通道或宿主 live 入口，不要自造通过证据，停在对应 `UNPROVEN/needs_user` 并指出唯一缺少的外部条件。
